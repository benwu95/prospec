### US-310: Incremental Knowledge Update [P0]

As a developer using Prospec,
I want AI Knowledge to be incrementally updated automatically when a change is archived,
so that module documentation stays in sync with the code without a full regeneration.

**Acceptance Scenarios:**
- WHEN a change is archived THEN automatically trigger the incremental update
- WHEN delta-spec.md exists THEN parse ADDED/MODIFIED/REMOVED to identify affected modules
- WHEN the update completes THEN return the list of updated/created/deprecated modules

#### REQ-SERVICES-021: Incremental Module Update
`updateModuleReadme` is create-only: it renders a skeleton README for a module that has none, and does nothing for a module whose README already exists. It never merges into or re-renders an existing README, because this project's module knowledge (Key Files purposes, Pitfalls, Modification Guide) lives **inside** the `prospec:auto` block — re-rendering that block from the mechanical scan context (a `"<name> module"` description, heuristic file descriptions) would gut the authored content, which is exactly why archive.service was decoupled from this service. README content updates are judgment and belong to the skill.
- WHEN the target README already exists, THEN the file is byte-identical afterwards (unit-pinned) and the caller is told its content update is pending
- WHEN the module is genuinely new, THEN its directory and a skeleton README are created for the skill to fill
- WHEN a REQ is REMOVED, THEN its module is listed as README-pending for the skill to remove that behavior, and is neither deprecated nor deleted

#### REQ-SERVICES-022: Index and Module Map Update
- WHEN module updated, THEN `{base_dir}/index.md` reflects latest state
- WHEN new module added, THEN module-map.yaml includes new entry
- WHEN module-map.yaml doesn't exist, THEN gracefully skip
- WHEN updating, THEN preserve each existing module's `category` (do not re-guess); an ADDED module gets an ordered `category` consistent with existing grouping

#### REQ-SERVICES-023: Knowledge Update Coordinator
`execute()` resolves the affected modules from the delta-spec (or from explicit module names), creates skeletons for genuinely new modules, and refreshes `{base_dir}/index.md` + `module-map.yaml` — but it **skips README regeneration for a MODIFIED or REMOVED REQ's module**, only acknowledging it so its index/module-map rows refresh. The result carries an explicit `readmePending` list: the coordinator's hand-off of the remaining judgment work to `/prospec-knowledge-update`. Before its first write in every mode, `execute()` judges `module-map.yaml` through `readKnownModules` (REQ-LIB-097) and, when that reports the map unreadable, refuses with a `PrerequisiteError` naming the cause and remedy it reports; after that judgment, this service reads `module-map.yaml` only through the knowledge-root-contained reader. After that judgment and before its first write, `execute()` resolves `module-map.yaml` and each processed module's `modules/<name>/README.md` against the knowledge root and `{base_dir}/index.md` against the base directory through `resolveContainedTarget`, and refuses with a `PrerequisiteError` when a target resolves outside its root, exists without being a regular file, is a file this run reads but may not read, or sits under a symlinked directory whose target does not exist — the root, or a directory above a missing root, included. It also refuses a target whose path — the target path of a symlink on it included — cannot resolve for a reason other than an absent entry, such as a directory that denies search permission, a component that is not a directory, a name longer than 255 bytes, or a symlink loop. When that root exists, every read and write of `index.md`, a module README and `module-map.yaml` goes to the real path the target resolves to inside it; the reported file paths are unchanged.
- WHEN `deltaSpecPath` is provided, THEN affected modules are parsed and resolved automatically; WHEN manual module names are provided, THEN only those are processed (and an unsafe name is refused before any write)
- WHEN a MODIFIED module is processed, THEN its index/module-map rows refresh, its name lands in `readmePending`, and no README byte is written
- WHEN a REMOVED REQ's module is processed, THEN it lands in `readmePending` like a MODIFIED one and keeps its `module-map.yaml` entry
- WHEN `module-map.yaml` needs no change, THEN it is not rewritten at all; when it does, the merge goes through the yaml Document so header comments and untouched descriptions survive
- WHEN the update is triggered as part of a larger flow, THEN a failure stays a non-fatal reported error
- WHEN `module-map.yaml` is a symlink resolving outside the knowledge root, THEN manual mode refuses with a `PrerequisiteError` whose message contains `resolves outside the knowledge root`, and the filesystem is byte-identical afterwards
- WHEN `module-map.yaml` exists but cannot be read, parsed or validated, THEN manual mode refuses with the cause and remedy `readKnownModules` reports and writes nothing
- WHEN `module-map.yaml` is absent, or is a symlink whose target does not exist, THEN manual mode creates the README skeleton and refreshes the index
- WHEN `module-map.yaml` is inside the knowledge root and passes the module-map schema, THEN the created, updated, README-pending, warning and generated-file output of delta-spec mode and manual mode is unchanged by the judgment
- WHEN delta-spec mode refuses an unreadable `module-map.yaml`, THEN its message ends with `no delta-spec REQ was classified`
- WHEN `{base_dir}/index.md` is a symlink resolving outside the base directory, THEN delta-spec mode and manual mode refuse with a `PrerequisiteError` whose message contains `index.md` and `resolves outside`, and the filesystem is byte-identical afterwards
- WHEN `index.md` exists but is not a regular file it can read (a directory, or a file without read permission), THEN `execute()` refuses before any write with a message naming `index.md`
- WHEN `modules/` or `modules/<name>/` is a symlink resolving outside the knowledge root, THEN manual mode and a delta-spec ADDED module are refused with a `PrerequisiteError`, no file is created outside the knowledge root, and the filesystem is byte-identical afterwards
- WHEN a processed module's `README.md` is a symlink resolving outside the knowledge root, THEN delta-spec mode refuses and writes nothing
- WHEN one of several processed modules has a README target outside the knowledge root, THEN no other module's README is created or rewritten
- WHEN `module-map.yaml`, `index.md` or a module README is a symlink to another file inside its root, THEN that target file receives the write and the path stays a symlink
- WHEN `index.md` or a module README is absent, or is a symlink whose target does not exist, and no refusal condition above applies to it, THEN it is created at that path
- WHEN the knowledge root does not exist yet, no directory on its path is a symlink whose target does not exist, and no refusal condition above applies to the README, THEN manual mode creates the README skeleton under it without refusing
- WHEN the knowledge root, the base directory, or a directory on the path to either is a symlink whose target does not exist, THEN `execute()` refuses with a `PrerequisiteError` naming that symlink and writes nothing
- WHEN `index.md`, the module READMEs and `module-map.yaml` are regular files inside their roots or absent, THEN the created, updated, README-pending, warning and generated-file output and the bytes written are unchanged by the target resolution
- WHEN manual mode meets an existing module README it may not read, THEN it does not refuse and lists the module as README-pending
- WHEN an exported README or index writer is called directly with a target that resolves outside its root or is not a regular file, THEN it refuses with a `PrerequisiteError` instead of reporting the module as README-pending
- WHEN a processed module's `modules/<name>/` directory denies search permission, THEN delta-spec mode and manual mode refuse with a `PrerequisiteError` whose message names `modules/<name>`, no module README is created, and the filesystem is byte-identical afterwards
- WHEN a processed module's `modules/<name>` is a regular file rather than a directory, THEN delta-spec mode and manual mode refuse with a `PrerequisiteError` whose message names `modules/<name>`, and the filesystem is byte-identical afterwards
- WHEN `index.md` or a processed module's README is a symlink loop, THEN delta-spec mode and manual mode refuse with a `PrerequisiteError` naming that link, and the filesystem is byte-identical afterwards
- WHEN `index.md` is a symlink whose target path runs through a regular file, THEN delta-spec mode and manual mode refuse with a `PrerequisiteError` naming that link, and the filesystem is byte-identical afterwards
- WHEN a manual module name is longer than 255 bytes, THEN manual mode refuses with a `PrerequisiteError` naming `modules/<name>` and `ENAMETOOLONG` before any write, whether or not `modules/` exists, and the filesystem is byte-identical afterwards

#### REQ-SERVICES-032: Feature-Prefix-Aware Module Resolution (Mint Guard)
When knowledge-update parses a delta-spec entry, it classifies the entry through `lib/knowledge-sync`'s `classifyDeltaEntry` (REQ-LIB-097), the same classifier and entry walk the knowledge-sync gate uses: the modules it acknowledges are the modules that classifier resolves for the delta-spec's entries, while the gate additionally checks `related_modules`. When `readKnownModules` reports `module-map.yaml` unreadable (it exists but cannot be parsed, the validating module-map reader rejects it, or it resolves outside the knowledge root), delta-spec mode refuses with a `PrerequisiteError` naming the cause and remedy `readKnownModules` reports — before classifying any entry or writing anything. A non-canonical REQ id is skipped with the existing `Skipped N non-canonical REQ id(s)` warning. An entry whose prefix hits the feature-map `req_prefixes` (a feature-prefix, not a module — the real source of phantom minting) resolves to `feature.modules ∪ relatedModules ∩ known`, and never treats the prefix as a module name to mint a phantom `modules/<prefix>/`; if resolution yields the empty set, skip + push a warning. Under a proven backfill a feature-slug prefix resolves the same way through the feature its `**Feature:**` header names and is never minted. An entry whose prefix is a known module resolves to that module, and an ADDED REQ with an unknown non-feature prefix still gets the new-module `src/<name>/**` skeleton; a MODIFIED or REMOVED REQ with such a prefix is skipped with a warning. A REMOVED REQ's modules are listed as README-pending — its behavior leaves the README — and are never deprecated or removed from the module map. `executeForChange` passes `relatedModules` and whether the change is a proven backfill, and loads the feature-map through the shared context.
- WHEN an entry prefix is a feature-map req_prefix and resolves to no known module, THEN skip that entry + warning, with zero filesystem writes (do not mint modules/&lt;prefix&gt;/)
- WHEN an entry's prefix is a known module, THEN it resolves to that module, as before
- WHEN an ADDED entry's prefix is neither a known module nor a feature prefix, THEN it still gets the new-module `src/<name>/**` skeleton
- WHEN a proven backfill's entry uses a feature-slug prefix, THEN it resolves through the feature its `**Feature:**` header names ∪ `relatedModules` ∩ known and nothing is minted
- WHEN a MODIFIED or REMOVED entry's prefix is neither a known module nor a feature prefix, THEN it is not listed as updated or README-pending and a warning names it
- WHEN a REMOVED entry names a known module, THEN that module is listed as README-pending and stays in `module-map.yaml`; its authored README content is left to the skill (only the mechanical sweep applies)
- WHEN one fixture holding ADDED, MODIFIED and REMOVED entries feeds both knowledge-update and the knowledge-sync gate's classifier, THEN the modules knowledge-update acknowledges equal the modules the classifier resolves
- WHEN `module-map.yaml` exists but cannot be parsed or fails its schema, THEN `prospec knowledge update --change` exits non-zero with one error naming `module-map.yaml` and its repair, reports no entry as neither a known module nor a feature prefix, and writes nothing
- WHEN `module-map.yaml` is readable, THEN delta-spec mode's created, README-pending and warning output is unchanged by the unreadable-map refusal
- WHEN `loadDeltaModuleContext` raises on the feature map (REQ-LIB-097), THEN delta-spec mode fails before classifying any entry or writing anything

#### REQ-CLI-026: `prospec knowledge update` Wires the Service, Scoped to What Is Safe
`prospec knowledge update [--change <name>] [--module <name>…]` gives the incremental knowledge-update service its first executable entry point (change selection through `change-resolver`), scoped to the operations that cannot destroy authored knowledge: delta-spec parsing, `updateIndex` (no-clobber) and module-map additions — a REMOVED REQ removes behavior from a README, never a module from the map. README **content** is out of scope — a skeleton is created only for a module that has none (REQ-SERVICES-021). The deprecated `prospec knowledge generate` subcommand is removed alongside it: generating README/index content is judgment and belongs to `/prospec-knowledge-generate`.
- WHEN the command runs over a module whose README already exists, THEN that file is byte-identical afterwards; a genuinely new module receives a skeleton README
- WHEN the run finishes, THEN index / module-map behavior matches the service's unit contract — a REMOVED REQ adds no deprecation banner and removes no module-map entry — and the report names the modules whose README content is still pending the skill's judgment
- WHEN `--change` names a change with no `delta-spec.md` (a `scale: quick` change, by contract), THEN it refuses and points at `--module`; a `--module` value that is not a safe resource name is refused before anything is written
- WHEN `prospec knowledge generate` is invoked, THEN it is no longer a registered command — and `/prospec-upgrade`'s previously stale `prospec knowledge update` reference now names a real one

#### REQ-TEMPLATES-162: knowledge-update Skill Delegates the Mechanical Half
`/prospec-knowledge-update`'s mechanical work collapses into a single `prospec knowledge update` call plus a review of its report, run as Phase 1; that report surfaces diff-attributed stamp-only modules — those a working-tree diff attributes but no REQ named (generated artifacts) — which need only a freshness stamp, not a README edit. Phase 2's source scan and description inference, Phase 2.5's format-drift consent dialogue, and Phase 3's README content authoring and verification stamp stay the skill's; Phase 3's 3e defines the affected modules to stamp as the modules `prospec knowledge update --change` reports as created or README-pending ∪ `metadata.related_modules` ∪ the modules a working-tree diff attributes through the module map (generated artifacts included) — so it never restates the classifier's rules — and notes the project's knowledge-sync gate (if any) is re-run after the feature commit, before push.
- WHEN reading the generated SKILL.md, THEN the mechanical steps are one `prospec knowledge update` invocation plus a result review, and the README-content step is marked as judgment
- WHEN a MODIFIED module has no module directory yet, THEN the skill runs `prospec knowledge update --module <name>` for the skeleton and then fills it
- WHEN the `index.md` auto block needs regenerating after curating `module-map.yaml`, THEN the skill re-runs the command instead of hand-editing the block
- WHEN README content review/update is completed for affected modules, THEN the skill explicitly instructs running `prospec knowledge verify <modules...>` to stamp `last_verified`
- WHEN Phase 1 reviews the report, THEN it surfaces the diff-attributed (stamp-only) modules the command reports — modules a working-tree diff attributes but no REQ named — as needing only a freshness stamp, not a README edit
- WHEN 3e names the affected modules, THEN it defines them as the modules `prospec knowledge update --change` reports as created or README-pending ∪ `metadata.related_modules` ∪ the modules a working-tree diff attributes through the module map (generated artifacts included) and notes the project's knowledge-sync gate, if any, is re-run after the feature commit and before pushing, worded project-agnostically with no literal script, filename, or CI-provider name
- WHEN a negative scan runs over the rendered `prospec-verify` and `prospec-knowledge-update` skills, THEN neither contains a repo-internal token (`knowledge:check`, `check-knowledge-sync`, `bundled-templates`) — including the pre-existing `knowledge:check` literal previously at the end of §3e, which is generalized to the project's knowledge-sync gate
- WHEN change-mode knowledge update refuses an unreadable, invalid or out-of-root module map, THEN the skill repairs the named input and retries change mode, without using --module to bypass that refusal

#### REQ-LIB-062: Working-tree changed-path attribution primitives
`changedPathsFromWorkTree(cwd)` lists the repo-relative paths a change has touched in the working tree, and `partitionDiffAttributedModules` maps them to modules and separates the ones no requirement named.
- WHEN called in a git work tree, THEN it returns changed tracked paths plus non-ignored untracked paths through lossless NUL-delimited Git capture and the same effective-input scope owner as snapshot-v2; generated source, documents and lockfiles remain included, while only `.prospec/` and Prospec-owned report constants are excluded
- WHEN the directory is not a git work tree, or any git capture fails, THEN it returns null (fail-closed), never an empty list read as "nothing changed"
- WHEN `partitionDiffAttributedModules(changed, moduleMap, acknowledged)` runs, THEN it attributes each path via `moduleAttributor`, returns the attributed modules as `diffAttributed`, and returns those absent from `acknowledged` (case-insensitive) as `stampOnly`
- WHEN a changed path is attributed to no module, THEN it contributes to neither set

### US-330: Module Knowledge Sub-Modularization [P1]

As a developer,
I want an oversized module README to be able to extract a functionally-independent sub-area into a sub-module file,
so that valuable detail is preserved while every module knowledge file — the README and each extracted sub-module — stays within the same token budget, rather than lossy trimming.

**Acceptance Scenarios:**
- WHEN a module README exceeds its resolved `l2_per_module` / `readme_max_lines` budget (defaults ≤1,000 tokens / ≤100 lines) and contains a content-rich, functionally-independent sub-area THEN extract it to `modules/{module}/{sub-module}.md`
- WHEN extracting a sub-module THEN the main README links it via a `## Sub-Modules` section
- WHEN loading a module README (L2) THEN also load its linked sub-modules

#### REQ-KNOW-016: Sub-Module Extraction over Lossy Trimming
- WHEN a module README would exceed its resolved `l2_per_module` token budget or `readme_max_lines` line budget (defaults ≤1,000 tokens / ≤100 lines, overridable via `.prospec.yaml` `knowledge.token_budget`) and contains a content-rich, functionally-independent sub-area, THEN extract it to `modules/{module}/{sub-module}.md` instead of trimming away detail
- WHEN extraction happens, THEN the main README links each sub-module from a `## Sub-Modules` section
- WHEN knowledge-generate runs, THEN Step 4.5 performs extraction and emits a skeleton `## Sub-Modules` section
- WHEN `prospec check` measures `knowledge-size`, THEN module Markdown files, including extracted sub-modules and supplementary docs, are measured individually against the same `l2_per_module` / `readme_max_lines` budget as the README

#### REQ-KNOW-017: Sub-Module Loading and Index Exclusion
- WHEN loading a module README (L2), THEN also load the `{sub-module}.md` files it links
- WHEN building `{base_dir}/index.md`, THEN never list sub-modules so L1 stays a lean top-level map; sub-modules are discovered only through `## Sub-Modules` links
- WHEN the `{base_dir}/index.md` Progressive Knowledge Loading Strategy renders, THEN L2 covers README + linked sub-modules

#### REQ-SERVICES-024: Sub-Module Maintenance on Update
- WHEN knowledge-update scans a module, THEN read its linked sub-modules
- WHEN a MODIFIED requirement enriches a module, THEN maintain or extract sub-modules instead of cramming detail back into the README

### US-340: Category-Grouped Module Index [P2]

As a developer navigating AI Knowledge in a project with many domain modules,
I want the `{base_dir}/index.md` module table to group by category into `### {Category}` sub-tables, with the classification single-sourced from `module-map.yaml`,
so that I can quickly locate modules by domain without manually maintaining a duplicated classification table.

**Acceptance Scenarios:**
- WHEN modules fall into ≥2 meaningful domain categories THEN `{base_dir}/index.md` groups them under `### {Category}` sub-headings, each sub-table keeping the same columns
- WHEN modules are only architectural layers (such as prospec itself) THEN keep a single flat table and do not add category to module-map
- WHEN module-map already has category THEN group by the first (primary) one without re-guessing; when category is missing, generate auto-infers a suggestion and writes it back

#### REQ-TYPES-028: module-map ModuleEntry Ordered category
`ModuleEntrySchema` adds an optional `category: string[]` (ordered, `[0]` = primary), backward-compatible (absent = flat table; `loadModuleMap` still loads existing maps without category); the single source of truth for classification.

#### REQ-KNOW-018: Knowledge Index 支援按 Category 分組渲染
`buildIndexTable` (CLI) groups the auto section into `### {Category}` sub-tables when all modules have a category and there are ≥2 primary categories; each sub-table has consistent columns, and `parseIndexModules` correctly enumerates all modules from the grouped output.

**Scenarios:**
- WHEN all modules have a category AND ≥2 primary categories exist THEN produce `### {Category}` sub-headings; OTHERWISE produce a single flat table (fail-flat)
- WHEN re-run THEN grouping is stable (by `module-map` declaration order) and the `prospec:user` section is preserved
- WHEN `parseIndexModules` parses the grouped output THEN the returned module count = the actual count (duplicate header/separator rows are skipped)

#### REQ-KNOW-019: Auto-Infer category and Persist It
`/prospec-knowledge-generate` infers a suggested category from path/keywords/domain semantics, writes it to `module-map.yaml` after user confirmation (bootstrap), and thereafter treats the file as authoritative (an existing category is not re-guessed); the user may manually override it — rendering and the source of truth share the same category value.
- WHEN a module has no category yet, THEN the skill proposes one and persists it after confirmation
- WHEN `module-map.yaml` already carries a category, THEN it is not re-guessed
- WHEN the index groups by category, THEN it reads the same persisted value
