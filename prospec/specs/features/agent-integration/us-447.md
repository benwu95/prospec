### US-447: Capability-aware station entry [P1]

As a developer maintaining a Prospec project across different AI coding hosts,
I want the station-transition guidance to prescribe the loading route the host's known skill lifecycle actually supports,
so that every station entry and re-entry obtains the required rules without trusting an unproven claim that context persists.

**Acceptance Scenarios:**
- WHEN the four supported hosts are synced, THEN a persistent-reattach host is told to invoke or re-invoke the station's canonical Skill natively with the status-printed file as fallback, and every other host is told to run `prospec status` and read the fallback skill file before any station action
- WHEN hosts share one output directory, THEN the protocol is rendered once from the whole group's merged capability, and a mixed or empty group falls back to the conservative read route
- WHEN the entry config or cascade protocol is rendered for any host, THEN it names no host tool, plugin agent type, vendor or installation root, and states that loading a station never means its references arrived

#### REQ-TYPES-100: Host skill lifecycle capability
The agent registry declares a closed skill_lifecycle capability with values persistent-reattach, tool-output and unknown. Capability declarations describe the documented host mechanism, not runtime availability or guaranteed token savings.
- WHEN reading the supported host entries, THEN Claude Code declares persistent-reattach, Codex declares tool-output, and Antigravity and Copilot declare unknown, with dated documentation or source provenance in registry comments; unsupported claims remain unknown.
- WHEN members share one output, THEN only a non-empty all-persistent-reattach group resolves to persistent-reattach; an all-tool-output group resolves to tool-output; an empty group or any other combination resolves to unknown, independent of member order or duplication.
- WHEN rendering without a lifecycle context, THEN guidance takes the conservative status-then-read branch and never claims persistence.

#### REQ-TEMPLATES-233: Capability-aware station entry guidance
Generated entry configuration and cascade loading guidance use the resolved skill_lifecycle capability, keeping canonical skill identity separate from host invocation syntax. Shared output is rendered once from the full group's capability, while init's provisional entry uses the same conservative policy for its actual output target.
- WHEN persistent-reattach guidance is rendered, THEN it instructs native skill invocation or reinvocation before every station action, with status and the resolved file path as fallback if native loading is unavailable.
- WHEN tool-output, unknown or absent capability guidance is rendered, THEN it instructs running prospec status before every transition or re-entry and reading the selected station's SKILL.md before entry checks, followed by references at their applicable phases.
- WHEN native loading or a fallback cannot provide the station instructions, THEN no station action proceeds on remembered rules; existing entry gates and receipt contracts still apply.
- WHEN rendering entry or cascade transition sections, THEN no host tool name, plugin agent type, model/vendor name or literal host installation root is embedded; existing host-labelled invocation matrices remain separate.
- WHEN syncing repeatedly or permuting shared-output members, THEN the generated protocol is stable and user-managed entry content is preserved.
- WHEN documenting and shipping the behavior, THEN both root READMEs and both CLI references describe the same capability-aware protocol, fallback and status identity; generated assets, affected Knowledge and factual counts are synchronized.
