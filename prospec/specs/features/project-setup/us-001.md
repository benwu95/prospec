### US-001: CLI Base Framework [P0]

As a developer,
I want a structured CLI entry point supporting `--help`, `--version`, and subcommand routing,
so that I can explore all available commands and know the tool version.

**Acceptance Scenarios:**
- WHEN executing `prospec --help` THEN display all available commands with descriptions
- WHEN executing `prospec --version` THEN display the version number
- WHEN entering an invalid command (e.g., `prospec inti`) THEN show an error and suggest the correct command

#### REQ-SETUP-001: CLI Entry Point and Command Routing
Provide the `prospec` command supporting `--help`, `--version`, and subcommand routing, following the `prospec <command>` or `prospec <resource> <action>` pattern.

**Scenarios:**
- WHEN executing `prospec --help`, THEN display all available commands with descriptions
- WHEN executing `prospec --version`, THEN display version from package.json
- WHEN entering invalid command (e.g., `prospec inti`), THEN suggest similar valid commands
- WHEN single-action command (e.g., `init`), THEN use `prospec <command>` format
- WHEN multi-action resource (e.g., change), THEN use `prospec <resource> <action>` format

#### REQ-SETUP-025: Git Work Tree Prerequisite at CLI Entry
Every command except the root `--version`, any `--help`, and the top-level `help`, `print-template` and `config` commands requires its project directory — the action's `--cwd` when given, otherwise the current directory — to be inside a git work tree. The `preAction` hook checks this after the `.prospec.yaml` existence check, running `git rev-parse --is-inside-work-tree` under the inherited environment, and refuses with a `PrerequisiteError` before the action runs. Apart from the `ConfigNotFound` refusal, requirements and acceptance scenarios of the non-exempt commands describe their behavior once both entry checks pass; those describing a directory outside a git work tree specify service and library behavior.
- WHEN no git executable is found, THEN the command exits non-zero, reports that git was not found, and suggests installing git
- WHEN the directory does not exist, or `git rev-parse --is-inside-work-tree` prints something other than `true` or fails other than by timing out while `git --version` succeeds — outside any repository, inside `.git`, a bare repository, or a directory git refuses — THEN the command exits non-zero, the message carries the failure's first error line when there is one, and the suggestion names `git init` and fixing the reported error
- WHEN `git rev-parse` times out, or fails while `git --version` fails too, THEN the command exits non-zero, reports that git cannot run with the first error line of `git --version`, or of `git rev-parse` when either call timed out, and the suggestion does not name `git init`
- WHEN the project sits in a subdirectory of a repository, THEN the check passes
- WHEN `mcp serve --cwd <dir>` runs, THEN the check runs in `<dir>`
- WHEN the existing `.prospec.yaml` existence check refuses a command, THEN `ConfigNotFound` is reported as before, ahead of the git check
- WHEN the check refuses a command, THEN no file is created or modified
- WHEN an exempt command runs outside a git work tree or without git, THEN its output and exit code are unchanged, and `--version` loads no module the check adds

### US-002: Config Validation and Error Handling [P0]

As a developer,
I want `.prospec.yaml` to have schema validation, and all commands to provide meaningful error messages,
so that I can quickly locate and fix configuration problems.

**Acceptance Scenarios:**
- WHEN `.prospec.yaml` is missing a required field THEN display the specific field name
- WHEN a command fails THEN the error message includes a problem description and a suggested fix
- WHEN `init --verbose` succeeds THEN show the completed initialization phases and actual artifact outcomes in addition to the normal summary; other commands retain their command-specific verbosity behavior

#### REQ-SETUP-002: Config Schema Validation
`.prospec.yaml` uses Zod schema validation with field-specific errors. CLI config diagnostics are advisory observations of the raw configuration; the existing reader and validator continue to decide command validity and preserve the established root-loose and nested-strip policies.
- WHEN `.prospec.yaml` is valid, THEN successfully parse all fields via Zod schema
- WHEN required fields are missing, THEN validation identifies their field paths, including project.name, and lists multiple schema issues together.
- WHEN a non-JSON project CLI action passes its existing entry gates and is eligible for config diagnostics, THEN inspect its target config once before the action and report unknown keys at finite object levels on stderr with their full field paths; diagnostics alone do not change command validity or exit code.
- WHEN computing an unknown-key suggestion, THEN choose a same-object schema key only when it is the unique nearest case-sensitive Levenshtein match within distance 2; ties and larger distances produce no suggestion.
- WHEN inspecting raw config, THEN inspect root, project, tech_stack, paths, test_evidence, knowledge, knowledge.token_budget and workflow object keys; free-key records, unknown-typed values and unknown-key subtrees remain opaque.
- WHEN root extension keys or nested unknown fields occur, THEN their existing passthrough or stripping policies remain unchanged; diagnostics neither auto-correct nor write config, and programmatic readConfig/validateConfig remain silent.
- WHEN config read or YAML parse fails during diagnostics, THEN diagnostics are omitted and the action's existing error owner remains responsible; diagnostics perform no schema or filesystem-topology validation.
- WHEN the action uses an existing --json mode, THEN suppress additional unknown-field text diagnostics and preserve its existing JSON payloads; non-JSON quiet diagnostics use stderr, and MCP diagnostics leave stdout untouched.
- WHEN invoking init, config example, print-template, help or version, THEN no config diagnostics are added; quickstart may diagnose an existing config and omits diagnostics when no config exists yet. The existing action target cwd also determines the diagnostic config path.

#### REQ-SETUP-003: Error Messages and Debug Mode
The shared CLI error formatter presents actionable typed errors. Initialization has distinct normal, verbose and quiet output modes; other commands retain their command-specific verbosity behavior.
- WHEN the shared formatter handles a ProspecError in human mode, THEN stderr includes its sanitized code, message and suggestion, and sets a nonzero exit code while retaining existing error-specific details.
- WHEN the existing JSON error path handles an error, THEN its code/message/suggestion and error-specific payload fields retain their existing structure; this contract does not add JSON dispatch to Commander usage errors or other entry paths.
- WHEN init succeeds in normal mode, THEN show its result summary, detected project context and next-step guidance.
- WHEN init succeeds in verbose mode, THEN additionally show the initialization phases actually completed and the actual per-artifact created, skipped or merged outcomes; retained curated files are reported as skipped, and a managed merge does not imply changed bytes.
- WHEN init succeeds in quiet mode, THEN stdout is empty and existing stderr warning behavior is preserved.
- WHEN producing init details, THEN service results record actual workflow outcomes independently of display mode; initialization retains its existing curated-file preservation, managed merge and config-last completion ordering.

- WHEN base_dir not configured, THEN use default value
- WHEN configured in `.prospec.yaml`, THEN use configured value

- WHEN `{base_dir}`, `{base_dir}/specs` or `{base_dir}/ai-knowledge` exists below the config's directory as a symlink or as a non-directory, or cannot be inspected, THEN validation fails naming `paths.base_dir` and that path; a path that does not exist yet is accepted
- WHEN config has `paths.base_dir`, THEN derive knowledgePath, constitutionPath, specsPath
- WHEN any service needs paths, THEN uniformly use `resolveBasePaths()`
- WHEN the path rules are documented, THEN the `.prospec.yaml` reference example and the configuration reference in both languages state the legal range of `paths.base_dir`, the symlink rule and that `knowledge.base_path` is no longer configurable, and the upgrading guide in both languages names the breaking change and how to move an out-of-range directory

### US-008: Init Language Selection and Language Policy [P1]

As a project owner who is not a native English speaker,
I want to choose the artifact and trust-zone document languages during `prospec init` and have the path-scoped Language Policy automatically written into the Constitution,
so that generated documents follow their configured zone languages without manually editing the Constitution.

**Acceptance Scenarios:**
- WHEN running interactive init THEN a primary language prompt appears (default English, custom input allowed)
- WHEN `init --language X` THEN skip the prompt and adopt X
- WHEN in CI mode (`--agents`) without the flag THEN adopt English with zero interaction
- WHEN init completes THEN `.prospec.yaml` records `artifact_language` and `trust_zone_language`, and CONSTITUTION.md contains a [MUST] path-scoped Language Policy
- WHEN CI init selects a non-English artifact language without `--trust-zone-language` THEN the trust-zone language remains English

#### REQ-SETUP-015: Init Primary Language Selection
`prospec init` provides primary language selection for both language axes: interactive input for `artifact_language` (default "English"), the `--language <lang>` flag, and English as the default in CI mode; and a trust-zone language resolved from `--trust-zone-language <lang>`, else English in CI mode, else English when the artifact language is English, else an interactive prompt defaulting to the artifact language. Both resolved values are written to `.prospec.yaml`.
- WHEN interactive init, THEN prompt for the document language with default English
- WHEN `--language X` (including `--language ""`), THEN skip the prompt; blank resolves to English
- WHEN CI mode without the flag, THEN English with zero interaction
- WHEN the resolved artifact language is English, THEN no trust-zone prompt appears and `trust_zone_language: English` is written
- WHEN the resolved artifact language is non-English and no `--trust-zone-language` is given outside CI mode, THEN a trust-zone prompt appears whose default is the artifact language; a blank answer resolves to that default
- WHEN `--trust-zone-language Y` is given, THEN the prompt is skipped and Y is written; a blank Y resolves to that path's default (English in CI mode, the artifact language otherwise)
- WHEN CI mode without `--trust-zone-language`, THEN `trust_zone_language: English` is written and CONSTITUTION.md plus the entry config are byte-identical to the rendering before this requirement changed
- WHEN `prospec init --help`, THEN the output lists `--trust-zone-language`

#### REQ-CLI-051: Init Output Reports the Resolved Trust-Zone Language
`formatInitOutput` names the resolved trust-zone language on the Document language line when the artifact language is non-English, and prints the pre-existing single-language line otherwise.
- WHEN `artifactLanguage` is non-English, THEN the line reads `for change artifacts; the trust zone (Knowledge base, specs/features, index.md, Constitution) in <trustZoneLanguage>` with the value passed through `sanitizeTerminal`, and never contains `English until set`
- WHEN `artifactLanguage` is English, THEN the Document language line is identical to the rendering before this requirement existed

#### REQ-TYPES-025: Config Language and Skill Triggers Schema

- WHEN the fields are absent, THEN legacy `.prospec.yaml` still validates; consumers treat the language as English
- WHEN `skill_triggers` values are not string arrays, THEN validation fails (ConfigInvalid)
- WHEN `trust_zone_language` is absent or blank, THEN the trust zone resolves to English and every generator renders exactly what it rendered before the field existed

#### REQ-LIB-013: Language Policy Constitution Rule
`languagePolicyRule(scope)` returns a [MUST] rule rendered from a resolved `LanguageScope` (REQ-LIB-030), stated **by path** so an audit decides by file location. Its form follows the two resolved languages: when both are English it renders the condensed single sentence (one zone, no exemption clause) unchanged from before the trust-zone axis existed; when both are the same non-English language it renders a single-language form naming both path sets under that language with code, identifiers, technical terms and git commit messages staying English and no exception clauses; when they differ it renders the two-zone form — change artifacts and their archived summaries in the artifact language, the trust zone (Constitution / README / index / `specs/product.md` / `specs/features/**` / knowledge base) in the trust-zone language, code, identifiers, technical terms and commit messages English, with the scope's named exceptions listed as non-violations in BOTH directions (trust-zone spots that may use the artifact language, and change-artifact spots that follow the trust-zone language because their content is copied into the trust zone verbatim). The two-zone form with an English trust zone is byte-identical to the pre-axis rendering; no form contains a literal asserting the trust zone is English. init places the rule first in `example_rules`.
- WHEN `init --language X`, THEN CONSTITUTION.md contains a [MUST] Language Policy rule rendering X and both path sets
- WHEN no language chosen, THEN the rule renders the condensed English form
- WHEN the rule and the entry config are compared, THEN both state the same path sets (they render from one scope)
- WHEN the scope carries reverse exceptions, THEN the rule renders them as a separate clause and its check states they are not violations; with none, the clause is absent
- WHEN the trust-zone language is non-English and differs from the artifact language, THEN the rule states the trust zone in that language, keeps code/identifiers/terms/commit messages English, and contains no `always remains in English`
- WHEN both languages are equal and non-English, THEN the single-language form renders both path sets under that language with no exception clauses
- WHEN `trust_zone_language` is unset or English, THEN the rendered rule is byte-identical to the pre-axis rendering
