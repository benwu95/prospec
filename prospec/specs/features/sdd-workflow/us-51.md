# SDD Workflow — Retained Worktree History

## US-51: Retain Terminal History Across Worktree Removal [P0]

As a developer working in linked Git worktrees,
I want complete archived and abandoned changes retained in the main worktree's corresponding project,
so that removing a worktree does not discard history needed for inspection, retry or learning.

**Acceptance Scenarios:**
- WHEN archive/finalize or abandonment completes and the source worktree is normally removed, THEN the complete bundle remains readable from the corresponding main-worktree project, while active workflow inputs and trust-zone writes remain source-scoped.
- WHEN surviving legacy terminal bundles are imported, THEN identical trees deduplicate and conflicting trees refuse without changing original bytes, identities or retry linkage.
- WHEN topology, transfer or publication cannot complete safely, THEN the operation refuses with actual retained paths and does not treat a partial destination as completed history.

**Independent Test:**
Real-Git worktree integration compares complete inventories before and after normal removal; unit and service tests cover topology, consumers, import conflicts and controlled I/O failures. Actual cross-filesystem execution is reported separately from fault injection.

#### REQ-LIB-104: Worktree-aware terminal history roots
A shared history-path resolver separates the executing Prospec project from the project that owns terminal history. Active changes, configuration, test inputs, delegation, Knowledge and spec writes remain scoped to the executing project.
- WHEN a registered linked worktree resolves its history, THEN archive and abandoned roots belong to the main worktree's corresponding project-relative directory, independently of branch names and trust-zone base_dir.
- WHEN the repository has a single worktree, THEN history remains under that project's .prospec directory; a proven non-Git project retains its existing local archive behavior and abandon retains its Git prerequisites.
- WHEN the main worktree or corresponding project is unavailable, the repository is bare, topology cannot be proven, or a target is unsafe, THEN resolution reports the cause without silently falling back to linked-worktree-local storage or creating a different project.
- WHEN a consumer reads shared history, THEN it applies containment against the resolved history project; source inputs retain their source-project containment and causal rechecks.
- WHEN the current linked project contains legacy local-only or conflicting terminal bundles, THEN history consumers disclose their location and the import remedy rather than silently merging them or claiming complete history; status still lists local active work.
- WHEN history roots are inspected or a dry run is requested, THEN resolution creates no directories, locks, operation records or other files.

#### REQ-LIB-105: Verified terminal bundle transfer
Terminal bundle transfer uses destination-local staging and explicit publication state to preserve inspectable data across filesystem boundaries and cooperative concurrent invocations. Its operation records are outside the saved bundle, leaving original artifact identities intact.
- WHEN a new native bundle is prepared, THEN a reserved versioned pointer identifies its external operation; a final destination receives this pointer before metadata or other artifacts, and a missing or invalid referenced operation is an error rather than legacy history.
- WHEN a transfer starts, THEN an exclusive project writer claim serializes destination admission, and a persistent operation records kind, source identity, actual source/staging/final paths, inventories and phase before data movement.
- WHEN the same source has an unfinished operation, THEN retries refuse without selecting another date or suffix; source identity distinguishes worktrees and project prefixes, so an unrelated same-named active change is not treated as that source.
- WHEN a bundle is copied, THEN enumeration and read-back compare file names, regular bytes and modes, directory modes and symlink targets without following symlinks; unsupported entries or changing source inputs refuse publication while preserving recoverable data.
- WHEN service-owned terminal preparation has completed, THEN an exclusively created final directory is verified against the prepared inventory before publication is marked; the mere existence of final or terminal metadata is not completion.
- WHEN publication succeeds, THEN cleanup rechecks the original source inventory before removing source artifacts; a changed or partially cleaned source is retained and reported alongside the complete final copy, and its active workflow remains blocked pending reconciliation.
- WHEN copy, preparation, publication, control writes or cleanup fail, THEN the command does not report success and exposes actual paths and phase; retries do not accept partial data as completed history or overwrite an existing destination.
- WHEN a process leaves an unresolved writer claim, THEN the system refuses competing writes and directs inspection rather than reclaiming ownership by elapsed time; recovery does not automatically restore user files or Git state.
- WHEN a transfer is complete, THEN authored archive summary edits and finalize can use the canonical bundle; the initial prepared inventory is not an immutable-content contract for later authorized edits.
- WHEN source and history share a filesystem, THEN the same copy/verify/publication guarantees apply as across filesystems; dry-run remains write-free.

#### REQ-SERVICES-129: Explicit legacy terminal history import
The history import service copies existing local terminal bundles into canonical history through the shared transfer owner, preserving source data and original identities.
- WHEN import names a project root, THEN it must be the current project or the same project-relative scope of an existing registered worktree sharing the same Git common-dir; a non-Git project permits only its own no-op import.
- WHEN a legacy archive bundle is imported, THEN its existing lenient metadata compatibility is retained; an abandoned bundle requires valid terminal metadata, a valid preservation manifest and readable preserved data consistent with its recorded hashes.
- WHEN import succeeds, THEN kind, basename, original metadata bytes, preservation manifest origin and retry linkage digests remain unchanged; the source bundle is retained.
- WHEN a legacy import is in flight, THEN a transient pointer makes partial publication distinguishable from unmarked legacy data; it is removed only after complete verified publication so the original bundle file set is retained. Marked modern inputs require valid history-owned operation lineage and are not treated as unmarked legacy bundles; they support only a canonical no-op or deduplication against an existing identical canonical tree and pointer. Non-canonical modern relocation is refused without rewriting origin or identity.
- WHEN the complete destination tree is identical, THEN import deduplicates; when the same identity has different content, THEN it refuses without rewriting, renaming or deleting either copy.
- WHEN an attempt is incomplete or data is missing/corrupt, THEN import reports the actual location and refuses that attempt without synthesizing contents from summaries.
- WHEN a batch partially succeeds, THEN its result identifies each imported, identical, conflicting or failed entry and an unfulfilled entry causes a nonzero CLI outcome; dry-run previews the same admissions without writes.

#### REQ-CLI-062: History location and import commands
The CLI exposes read-only history paths and explicit history import commands through services, using typed results and the existing output conventions.
- WHEN prospec history paths is invoked, THEN it reports resolved execution/history roots and local-only or pending diagnostics; --json emits structured results without mutations.
- WHEN prospec history import --from <project-root> is invoked, THEN it calls the history import service; --dry-run previews without writing and --json emits its structured outcome.
- WHEN human output includes repository-derived text or paths, THEN it passes the existing terminal sanitizer; refusal and partial outcomes remain visible as errors and never imply that worktree removal is safe before complete preservation.
- WHEN docs and shipped guidance direct archive, abandon, retry or learn work, THEN they use CLI-reported canonical locations and distinguish local history retention from Git commits or cross-machine backups.

#### REQ-TESTS-136: Worktree terminal history regression matrix
Regression tests exercise terminal history through real temporary Git worktrees and service/CLI consumers, with failure injection reserved for boundaries that need controlled faults.
- WHEN archive/finalize and abandon scenarios complete and their linked worktree is removed without force, THEN the main project's complete bundle matches the pre-removal inventory, including final summary and abandoned preservation.
- WHEN topology scenarios run, THEN single worktrees, non-main branch names, project prefixes, multiple monorepo projects, missing main projects, bare repositories and unsafe roots have explicit expected results without cross-project writes.
- WHEN consumer scenarios run, THEN status, retry/Premise linkage, finalize and learn read the same canonical histories while active workflows and trust-zone writes remain source-scoped.
- WHEN same-named archives from different worktrees or dates are interleaved, THEN exact finalize selects its originating bundle, ambiguous legacy/import selections and known foreign origins refuse, and unrelated bundles and source specs remain byte-identical.
- WHEN migration and failure scenarios run, THEN identical/conflicting legacy bundles, source changes, writer races, unfinished origins, copy/publication/control/cleanup failures preserve inspectable data and reject false completion.
- WHEN cross-filesystem claims are reported, THEN actual cross-filesystem execution is distinguished from injected errors and unavailable environments; dry-run verifies both source and history trees remain unchanged.
- WHEN guidance contracts run, THEN removing canonical-location instructions or the preservation/restoration boundary fails the relevant section-scoped assertion independently of token-count baselines.
