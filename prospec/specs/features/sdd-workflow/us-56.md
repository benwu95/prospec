# SDD Workflow — Non-Convergence Discipline at Existing Decision Points

## US-56: Adversarial Loops Converge Because Each Decision Point Carries Its Discipline [P1]

As a developer whose plan verifier and review run as adversarial loops,
I want explore, new-story, plan and review to settle an input's legal range and a series split before design, let an external tool produce its own judgment, keep a tool's end result out of the Spec, honor stated stop conditions, and converge wording loops and claim refutations by fixed rules,
so that a loop stops patching around undefined scope or a reinterpreted tool and ends at a predictable point instead of a new reason each round.

**Acceptance Scenarios:**
- WHEN fixes in plan or explore keep landing on boundary values of an input with no defined legal range, THEN the agent stops guarding each consumer and has the range defined in a prerequisite change
- WHEN new-story or explore finds behavior this change keeps only for a later change in the series to remove, THEN that behavior and its removal are scoped as one change
- WHEN a design applies an external tool's semantics to input, THEN the agent first lists each caller's input shapes and applies the semantics directly only to input that tool produced
- WHEN a design needs an external tool's judgment, THEN the first candidate has the tool produce it, and a new mechanism that still interprets the same tool's output is not a new premise
- WHEN re-compare or candidate comparison proposes an alternative mechanism, THEN the comparison names the existing gates it makes newly dependent
- WHEN a delta-spec claim concerns an external tool's end result across its input sources, THEN the Spec states only the component's own output, flow and warnings, a real-tool scenario-matrix test pins the end result, and the claim class is deleted at its second counterexample
- WHEN a stop condition the agent stated to the developer is reached, THEN its action is the first recommendation, and recommending anything else first names the overturned premise
- WHEN the same need repeatedly fails to converge, THEN the agent quantifies the actual impact of leaving it undone before recommending more attempts
- WHEN only wording findings remain in a plan-verifier loop, THEN the agent classifies each affected clause once, fixes only false clauses and imprecise ones this change rewrote, and converges at no FLAWS and no false clause
- WHEN review judges a documented claim false, THEN the refuting counterexample falls inside the subject's existing definition in the project's documents and Feature Specs

#### REQ-TEMPLATES-260: Explore and new-story bound a change's scope before design
`prospec-explore`'s Impact Space and `prospec-new-story`'s requirements gathering check a change's boundaries before design starts.
- WHEN an exploration weighs a design's impact, THEN the Impact Space questions include whether the design depends on an input whose legal range is undefined, whose answer is to define that range in a prerequisite change rather than guard each consumer against its boundary values
- WHEN an exploration or a story's requirements gathering finds behavior that this change would keep only for a later change in the same series to remove, THEN that behavior and its removal are scoped as one change, and a Draft-First story records that scoping in its Stated Assumptions
- WHEN these checks render, THEN each is one general statement inside the existing Impact Space list or Phase 1 list, and neither adds an artifact, a CLI gate or a stop point

#### REQ-TEMPLATES-261: The external-research partial lets a tool produce its own judgment
The `_external-research` partial carries one rule on external tools' judgments, rendered wherever the partial renders.
- WHEN a design needs an external tool's judgment, THEN the partial names having the tool produce that judgment as the first candidate
- WHEN a design applies an external tool's semantics to input, THEN the partial has the design apply them directly only to input that tool itself produced, after listing the input shapes each caller passes; other input is parsed first or scoped out as separate work
- WHEN the rule renders, THEN it is one bullet of the partial, the set of skills that include the partial is unchanged, and it names no specific tool, file, host, model or vendor

- WHEN the criterion renders, THEN the measured winners still follow the metrics table, and the metrics table, the decision rules and the candidate and decision payload schemas are unchanged

#### REQ-TEMPLATES-263: Spec claims leave an external tool's end result to a real-tool test
`delta-spec-format.md` keeps an external tool's end result out of the Spec, in a sentence that follows its Claim writing list.
- WHEN a Spec describes behavior that depends on an external tool, THEN the sentence after Claim writing has it state the component's own output, flow and warnings rather than the tool's end result across that tool's input sources, pin that end result with a scenario-matrix test against the real tool, and delete the claim class once a second counterexample of that class appears
- WHEN the rule renders, THEN the Claim writing list it shares with the Docs-Claims lens is unchanged, it names no specific tool, and it adds no Startup Loading item

#### REQ-TEMPLATES-264: The human-decision contract keeps stated stop conditions and weighs leaving work undone
The `_human-decision` partial binds a recommendation to the stop conditions already stated and to the measured cost of stopping.
- WHEN the agent has already stated a stop condition to the human and that condition is reached, THEN the agent recommends the stated action as the first option, and recommending anything else first names the premise that was overturned
- WHEN the same need has repeatedly failed to converge, THEN before recommending further attempts the agent quantifies the actual impact of leaving it undone — real usage and the safeguards already in place — as evidence for the recommendation
- WHEN these rules render, THEN they render wherever the partial renders, add no question where the station decides autonomously, and add no decision point beyond the existing ones

#### REQ-TEMPLATES-265: The plan-verifier rubric converges a wording-only loop with a one-time clause audit
`plan-verifier-rubric.md` states how a wording-only verifier loop converges.
- WHEN a plan is to be revised again and, once FLAWS are triaged, its verifier's remaining findings are wording only, THEN the plan stops revising round by round, classifies every clause of the affected text once as holding, imprecise or false, fixes only the false clauses and the imprecise clauses this change rewrote — deleting by default — and re-verifies; the loop has converged when that round reports no FLAWS and none of its warnings names a false clause
- WHEN the rule renders, THEN the Verdict & Severity Contract rows, the five dimensions and the report schema are unchanged

#### REQ-TEMPLATES-266: A review finding refutes a claim only within its subject's definition
`review-format.md` bounds the counterexample a finding uses to refute a claim.
- WHEN a reviewer's finding judges a claim false, THEN the finding-content rules require its counterexample to fall inside the existing definition of the claim's subject in the project's documents and Feature Specs, a rule that governs the reviewer's output rather than the change
- WHEN the rule renders, THEN the severity criteria, the findings-table columns and the review-lens criteria rows are unchanged
