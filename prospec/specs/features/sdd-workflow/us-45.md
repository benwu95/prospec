### US-45: Delegated Reviewers and Graders Are Isolated, Their Mutations Detected and Preserved, Recovery Handed to the Human [P0]

As a developer delegating review lenses, verifiers and verify graders to fresh-context subagents on any host (Claude Code, Codex, Copilot, Antigravity),
I want the CLI to ticket every delegate before it spawns — capturing the five repository facets (content, HEAD, index, local refs, stash), copying the uncommitted work into a checkpoint under the change directory and building a snapshot the delegate works in — and to refuse the delegate's payload, the review merge and the verify record whenever a facet changed, handing recovery to me with the checkpoint's copies rather than writing my tree, index, HEAD or refs itself,
so that a delegate that damages the working tree stops the flow at the receipt instead of being graded on a mutated state, the damaged bytes are still there to recover from, and the isolation is the same path on every host without a host-specific guard.

**Acceptance Scenarios:**
- WHEN a delegate edits a tracked file, moves HEAD, changes the index (skip-worktree and assume-unchanged flags included), adds or drops a stash entry, or moves a local branch after its ticket was issued, THEN `prospec change delegate --receive` exits non-zero, names the facet with its before and after values and the checkpoint path, and `review merge` / `verify record` refuse while that attempt is open or refused
- WHEN every facet is unchanged, THEN the receipt passes and the sink prints one settlement line disclosing the round was covered by mutation detection; a round with no ticket, or whose delegations all ended with `--spawn-failed`, is disclosed as not covered
- WHEN a ticket is issued, THEN `.prospec/changes/<name>/.delegated/<stem>.checkpoint/` holds a byte copy of every uncommitted, untracked, non-ignored file and of the index, nothing under `.git` is written (a read-only `.git` still issues), and the payload path `<station>-<role>-<round>-<attempt>.json` is assigned by the CLI — a leftover at that path, a stale payload, or a superseded attempt is refused
- WHEN the tree is not back at the pre-spawn state after a refusal, THEN a new attempt of any key and an ordinary `--spawn-failed` are refused until it is; only an explicit human `--accept-current-tree` records the acceptance, keeps the checkpoint and is disclosed by the sink
- WHEN `agent sync` renders the five delegating stations for the four hosts, THEN the delegation instructions are identical, the snapshot is built by the CLI under `os.tmpdir()` with a self-checked content digest, no `can_*` capability gates it, and no subagent definition, hook or permission file is produced; a snapshot that cannot be built (a shallow repository, a live split index, an assume-unchanged file, no index yet, a tree that moved while the ticket was issued, a digest that does not reproduce) refuses the issue by name and the station grades in-session with the round disclosed as not covered
- WHEN the shipped templates and user documents are read, THEN the Physical Receipt protocol's step definitions live only in `delegation-protocol.md` (the other nine surfaces carry a one-line pointer), the bounded wait and single re-spawn are declared there, the claims say "detect and preserve" (never prevent, block or restore), the threat model is accident-not-malice, and the blind spots (ignored files, artifacts under `.prospec/`, unread `.git` metadata, planted hooks or config, processes outliving the delegate, pushes, parallel changes in one repository) are listed

**Independent Test:**
Unit pins for every facet change and every receipt, failure and settlement judgment; e2e drives ticket → edit / `reset --soft` / `reset --hard` / branch switch / `stash drop` / `skip-worktree` → refused receipt and refused merge, then a hand recovery from the checkpoint and a new attempt; contract tests scan the rendered surfaces for the single protocol definition, the claim vocabulary and the absence of host-specific artifacts, and a `child_process` grep pins `lib/git-read.ts` as the delegation path's only spawner.

#### REQ-LIB-090: `lib/repo-state.ts` captures and compares the repository state read-only
`captureRepoState(cwd)` reads five facets through git reads only. The git calls this module makes itself go through `lib/git-read.ts`, whose closed `GIT_READ_SUBCOMMANDS` set holds only reading invocations (`rev-parse`, `ls-files`, `for-each-ref`, `status`, `symbolic-ref` in its read form only — exactly one ref argument and no option other than `-q` or `--short`, so `-d`/`--delete` and the two-argument write form are refused — and `reflog` only as `reflog show` with no option other than `--format=<format>`, so log's `--output=<file>` is refused), runs with optional locks disabled and with the repository-selecting and pathspec-interpreting environment fixed (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_COMMON_DIR`, `GIT_LITERAL_PATHSPECS`, `GIT_GLOB_PATHSPECS`, `GIT_NOGLOB_PATHSPECS`, `GIT_ICASE_PATHSPECS` removed from the child environment, so an inherited `GIT_DIR` cannot redirect a read to another repository and an inherited `GIT_LITERAL_PATHSPECS` cannot turn the whole-index pathspec `:/` into a file name that matches nothing), and throws before running a subcommand, an option, or an argument shape outside the set. Three reads reuse `drift-sources`' own readers unchanged rather than the allowlist — the content facet's base (`computeChangeState`), the checkpoint's changed-path listing (`workTreePaths`, a `status --porcelain=v1 -z` read), and the project prefix (`gitProjectPrefix`) — each read-only by construction (`status`, `ls-files`, `rev-parse` only) and each called with `GIT_OPTIONAL_LOCKS=0` in the environment by every delegation caller, so no `git status` on the delegation path refreshes the index's stat cache; none of them alters a facet. Because `computeChangeState` deliberately excludes the report `prospec check` writes at the project root (`prospec-report.json`), the content facet hashes that digest together with that file whenever it is tracked or untracked and not ignored (their bytes and executable bit — the one mode bit git reproduces —, a symlink's target, or their deletion), through the allowlisted `ls-files`, so a delegate rewriting it in the main tree is detected; an ignored report file stays unseen, like every ignored file. The index facet's `ls-files` listing goes through the allowlist's lossless record reader (`gitReadRecords`), not through `drift-sources`' executor: `content` is the `computeChangeState` digest (the project's non-ignored files outside `.prospec/`) combined with the root report file above; `head` is the symbolic ref (or detached), the commit (null when unborn), and which in-progress operation markers exist (`MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `rebase-merge`, `rebase-apply`, `sequencer`, `BISECT_LOG`, probed read-only through `git rev-parse --git-path`); `index` hashes each staged entry's mode, object id, stage, path, skip-worktree flag, and assume-unchanged flag — over the whole index, so a project nested in its repository still sees an entry outside its own subtree —, never stat data; `refs` lists local refs other than `refs/remotes/`, the `refs/prefetch/` mirrors `git maintenance` writes, and `refs/stash`; `stash` lists every entry of the stash reflog. `diffRepoState(before, after)` is a pure function returning the changed facets with both values, and it is the only facet comparison in the code base.
- WHEN any facet cannot be read, THEN the capture returns that facet as unreadable with the reason, and no caller treats it as unchanged
- WHEN `gitRead` is asked for a subcommand outside `GIT_READ_SUBCOMMANDS`, a `symbolic-ref` with any option other than `-q`/`--short` or with more than one ref argument, a `reflog` other than `show`, or a `reflog show` with an option other than `--format=<format>`, THEN it throws before any process starts; the delegation modules (`repo-state`, `delegation`, `delegation-checkpoint`, `change-delegate.service`) import no `node:child_process` of their own — their own main-repository git reads go through `git-read`, their remaining reads through the three `drift-sources` readers named above, and only the snapshot builder's `gitSnapshot` runs other subcommands (`clone`, `config`, `remote`, `checkout`), each with the same fixed environment plus `GIT_DIR` set explicitly to the snapshot's own `.git`, with its working directory set to the snapshot root, its destination — an absolute path, judged on its real path — asserted to lie directly under that root with the snapshot prefix, and only a closed per-subcommand set of options admitted (`clone`: `-q`, `--shared`, `--no-checkout`; `config`: none; `remote`: `--push`; `checkout`: `-q`, `--detach`), so an option naming a path such as `config --file` or `clone --separate-git-dir` throws before any process starts
- WHEN only the index's stat cache is refreshed (as a `git status` outside the delegation path does), or a remote-tracking or prefetch ref moves (as `git fetch` and `git maintenance` do), THEN no facet changes; a tag a fetch auto-follows is a local ref and does change the refs facet
- WHEN a tracked file's bytes, HEAD's branch or commit, an in-progress operation marker, a staged entry or its skip-worktree or assume-unchanged flag, a local branch or tag, or any stash entry (not only the newest) changes, THEN `diffRepoState` reports that facet

#### REQ-LIB-091: `lib/delegation-checkpoint.ts` builds the snapshot and keeps the checkpoint
The snapshot is a separate repository under the real temporary directory: a shared, non-checkout clone of the main repository with its hooks disabled in its own config and its `origin` push URL disabled (the main repository's local branches stay available as `origin/<branch>` for diffs), checked out detached at the issue-time HEAD, with the checkpoint's uncommitted content overlaid, the main index's bytes copied in as the snapshot's own index (its objects are reachable through the shared alternates, so staged additions stay staged), and a marker holding the ticket's stem and nonce. The checkpoint lives under `.prospec/changes/<name>/.delegated/<stem>.checkpoint/`: a byte copy of every dirty, staged-added, and untracked non-ignored file in the digest's scope — the two root report files the content facet covers included —, the deleted-path list, and the raw bytes of the main index; a symlink is kept as its recorded target in the entry list, never as a symlink under `.prospec/`, so the directory never holds a link that dangles. Neither is built by writing the main repository's `.git`, and the module exposes no function that writes the human's tree — the working tree outside `.prospec/changes/<name>/`, where the CLI's own records (tickets, checkpoints, `metadata.yaml`) live —, the index, HEAD, or refs; the snapshot builder's git calls run with `GIT_DIR` set explicitly to the snapshot's own `.git` and the other repository-selecting variables removed, so an inherited `GIT_DIR` cannot point them at the main repository. When the CLI first creates a change's `.delegated/` directory it writes a `.gitignore` containing `*` there, so copies of uncommitted bytes are never committed in a project that tracks `.prospec/changes/`.
- WHEN a snapshot is built, THEN its content facet — computed by the same function as the pre-spawn one — at the project's own path inside it (the prefix read through the lossless project-prefix reader `drift-sources` owns) must equal the pre-spawn content digest, or it is removed and no ticket is issued — a snapshot whose content cannot be read back is refused naming the read error rather than a filter; a shallow repository (whose shared clone gets no alternates), a repository whose index is currently linked to a split index (`core.splitIndex` — a `sharedindex.*` file the index still names; one left behind after `--no-split-index` is not a link), a tracked file marked assume-unchanged (whose changes `git status` cannot list for the checkpoint), a repository with no index yet, and an index that cannot be inspected are each refused before the clone with their named reason
- WHEN a snapshot is released, THEN it is deleted only when its real path lies directly under the real temporary directory, its name carries the ticket's snapshot prefix, and its marker's nonce equals the ticket's; a path a ticket merely names is never deleted, and no repository-wide `git worktree prune` runs
- WHEN a checkpoint is written, THEN its directory is created exclusively first (a concurrent issue of the same attempt stops before touching the winner's copies), each copy is written whole and its sha256 recorded in the entry list, and the index copy's sha256 is recorded, so the human can verify a copy before using it
- WHEN a checkpoint is released, THEN the path is derived from the change directory and stem — never from a ticket field — and a release that fails is reported, never thrown

#### REQ-LIB-092: `lib/delegation.ts` issues, receives, fails, and settles delegations
`src/lib/delegation.ts` owns the ticket lifecycle at `.prospec/changes/<name>/.delegated/<stem>.ticket.json` with the payload path `.prospec/changes/<name>/.delegated/<stem>.json`; `judgeIssue`, `judgeReceipt`, `judgeFailure`, and `judgeSettlement` are pure functions over collected facts, and the module writes only under `.prospec/changes/<name>/.delegated/`, the change's `metadata.yaml` (through the failure hook), and the snapshot directory — never the human's tree (the working tree outside `.prospec/changes/<name>/`), the index, HEAD, or refs. Ticket transitions assume one orchestrator running them in sequence: each transition re-reads the ticket immediately before its write and refuses when the state on disk no longer equals the state it judged, which narrows — not closes — the window between two transitions of one stem run concurrently; because every verdict is judged against the state both read, a lost update can only replace one admissible verdict by another, never admit a payload the judgment refused.
- WHEN a ticket is issued, THEN the pre-spawn state, the checkpoint, and the snapshot (with its self-check) come first, the five facets are captured once more and the issue is refused — naming the facets with both values — when they differ from the pre-spawn state (a snapshot self-check that fails because the tree's own content moved since the capture is refused the same way, as a retry rather than a degradation), so the ticket never describes one state while its copies hold another, and the ticket file appears last, written whole to a temporary file, validated against the ticket schema, and linked without clobbering, so a failure at any step leaves neither a ticket, a checkpoint, nor a snapshot; a leftover checkpoint counts toward the next attempt only when its name carries an attempt a ticket could hold
- WHEN a ticket is issued for a key, THEN its attempt is one more than the key's highest — counting a checkpoint left behind by a ticket that no longer exists, so no stem is reused —, it is refused when the assigned payload path already exists, and it is refused when any key's latest non-consumed attempt of this change that is `open` or `refused` has a pre-spawn state that differs from the current state (the refusal names that ticket, its changed facets, and its checkpoint path, and states that the tree must first return to the pre-spawn state; superseded attempts are not consulted), so every ticket open at the same time shares one pre-spawn state; tickets of other changes in the same repository are not consulted
- WHEN a payload is received, THEN only an `open` ticket that is its key's latest attempt is judged; any readable facet that changed makes it `refused` as mutated with the full observed state, unreadable facets recorded as such — even when the payload is missing —, and the refusal names each changed facet with its pre-spawn and current values and the checkpoint path, and states that recovery is the human's; only when every readable facet is unchanged and some facet cannot be read does it stay `open`, and the ticket then records that its delegate returned with an unreadable facet; a refused ticket keeps its snapshot and checkpoint; otherwise a missing, empty, or not-yet-complete payload (the detail names the parse error) leaves it `open`, a schema failure or a payload older than the issue time (compared in whole seconds) makes it `refused`, and a passing one makes it `received`
- WHEN an `open` or `refused` ticket is ended as failed without a human acceptance, THEN it is refused while any facet differs from its pre-spawn state (naming the facets and the checkpoint path); no other ticket's state restricts it; the service's warning is written through a hook the lib calls after every check and before the ticket turns failed
- WHEN a ticket is ended with an explicit human acceptance, THEN the acceptance is recorded whatever facets could be read (an acceptance whose state cannot be captured at all is refused); it is refused while any other latest attempt of the change is still `open` without a recorded return (a running delegate would lose its snapshot and its later damage would go unseen — receive it or end it first), and otherwise ends every `refused` latest attempt, and every `open` one whose delegate returned with an unreadable facet, in the same operation, writing one warning per ended ticket; the checkpoint of every ticket ended by acceptance is kept and its path named, because it may hold the only copy of what was lost
- WHEN a sink settles a station, THEN only each key's latest attempt counts, judged over every attempt of the key so that an attempt a consumed one superseded never blocks again: a latest attempt that is `open` or `refused` refuses with the remedy, and otherwise the verdict carries the received, failed, and human-accepted counts plus — over every attempt of the settled keys, superseded ones included — the number refused as mutated, or `not-ticketed`
- WHEN a ticket becomes `received`, `consumed`, `failed` without acceptance, or a newer attempt supersedes it, THEN its checkpoint is released at the path derived from the change directory and stem and its snapshot — whose path the ticket records — is deleted only when REQ-LIB-091's three release conditions hold; a `refused` ticket and a ticket ended by acceptance keep their checkpoint; a release that fails is reported, never thrown, so it cannot undo a ticket already written

#### REQ-SERVICES-120: `prospec change delegate` issues, receives, and fails delegations
`prospec change delegate` runs one of three mutually exclusive modes: issue (`--station <review|verify> --role <role> --round <n>`), receive (`--receive <stem>`), and fail (`--spawn-failed <stem> --reason <text> [--accept-current-tree]`). The CLI records the pre-spawn state, checkpoint, snapshot, issue time, and attempt itself; the orchestrator supplies only the station, role, and its own round counter. No mode writes the human's tree (the working tree outside `.prospec/changes/<name>/`, the CLI's own record directory), the index, HEAD, or refs, and every mode runs its git reads with `GIT_OPTIONAL_LOCKS=0`.
- WHEN a ticket is issued, THEN `--role` is normalized through `formatDelegationRole` (so `--role verifier-C-1` issues `verifier-c-1`), and the command prints the resulting stem, the absolute payload path and the absolute snapshot path, on every host
- WHEN a receipt fails or is refused, THEN the command exits non-zero with the reason and remedy, and a mutation refusal names each changed facet with its pre-spawn and current values and the checkpoint path, and states that the flow stops here: the orchestrator recovers with git and the checkpoint files only with the human's consent, and issues a new attempt only once the tree is back at the pre-spawn state, or the human ends the attempt with `--accept-current-tree`
- WHEN `--spawn-failed` ends a ticket, THEN a `quality_log` entry `{skill: prospec-delegation, result: WARN}` naming the station, role, round, attempt, and reason — plus a refused ticket's recorded reason and changed facets — is appended first, and only then does the ticket become `failed`; when a human acceptance keeps a checkpoint (REQ-LIB-092), the command names its path
- WHEN such a `prospec-delegation` entry exists, THEN it neither closes a review round nor stands in for review provenance

#### REQ-SERVICES-121: `review merge` and `verify record` refuse an unsettled delegation
`review merge` and `verify record` settle their station's delegations after resolving the change and before every pre-existing refusal and write, whatever form their input takes (a `--findings` file, a `--dimensions` file, or flag-form `--dimension` values).
- WHEN the settlement refuses, THEN the command exits non-zero with the ticket, the reason, and the remedy, and `review.md`, `verify.md`, and `metadata.yaml` stay byte-identical
- WHEN the settlement admits, THEN the sink proceeds exactly as before, then marks every live attempt of the station `consumed`, superseded attempts included (a failure to mark is a warning), and prints the received, failed, and human-accepted counts and how many attempts were refused as mutated
- WHEN no settled ticket was received, THEN the output says the round was not covered by delegate mutation detection — naming the failed attempts when every delegation failed, and otherwise the two causes it cannot tell apart: none was issued, or an earlier run of the sink already settled them; the line is never omitted from the normal output
- WHEN a sink is replayed, THEN the delegation ticket states count among its inputs: a re-run after the first run consumed the tickets sees different inputs, so its settlement line may differ while every other byte of output and every write stays as before
- WHEN the review loop has applied fixes after a received delegation, THEN the merge is not refused for the changed tree, because the mutation judgment already ran at receipt

#### REQ-TEMPLATES-238: The delegation-protocol reference is the single receipt definition
`references/delegation-protocol.md` — deployed with `prospec-review`, `prospec-verify`, `prospec-plan`, `prospec-tasks`, and `prospec-ff` — is the one definition of the Physical Receipt Verification Protocol and of the delegation ticket flow, with the await bounds rendered from `DELEGATION_AWAIT`, the same text on every host, and its size within the reference budget.
- WHEN a delegation is described, THEN the order for review and verify is: issue the ticket (one role per delegate of a round — `lens-<name>`, `verifier-<finding id>`, `grader` (verify 2/5 and 3/5), `grader-design` (verify dimension 6) — since a second ticket for a role is a re-spawn), spawn with the absolute payload and snapshot paths, receive when the delegate returns, then call the sink; the orchestrator changes nothing in the working tree between issue and receipt; the other stations apply the receipt checks and the bounded wait without a ticket
- WHEN a payload has not arrived, THEN the wait is bounded by the declared idle minutes or poll count; the orchestrator re-spawns exactly once (under a new ticket at review and verify), and a second failure takes Harness Degradation with the grading context disclosed; stations without a ticket record the failure under `prospec-delegation`, never their own label
- WHEN a facet stays unreadable past the bounded wait while every readable facet is unchanged (a nested repository, a symlink leaving the represented inputs), THEN the orchestrator first names the cause for the human to remove and receives again; if the human keeps the tree, one `--accept-current-tree` ends that attempt together with every sibling that returned the same way
- WHEN a receipt is refused as mutated, THEN the flow stops: the orchestrator presents the changed facets with their values and the checkpoint path to the human, and recovers — using git and the files under the checkpoint — only what the human agrees to, never by a CLI command; a new attempt is issued only once the CLI finds the tree back at the pre-spawn state (it refuses otherwise) and only on the human's explicit go-ahead — the orchestrator never re-issues after a mutation refusal on its own, so the loop is bounded by one human decision per refusal, and such a recovered attempt is not a re-spawn and does not consume the re-spawn allowance, which counts only spawn failures and exhausted waits; the human alone may instead end the attempt with `--accept-current-tree`, which keeps the checkpoint; a refusal whose tree already equals its own pre-spawn state (a parallel delegate's change, recovered under that delegate's ticket) goes straight to a new attempt; a verifier's role is `verifier-` plus the finding id normalized by `formatDelegationRole`
- WHEN a ticket cannot be issued (not a git repository, a shallow repository, a split index, a file marked assume-unchanged, no index yet, a sparse or gitlink input, or a snapshot that does not reproduce the tree under the repository's filters, each refused with its named reason), THEN the station never spawns an unticketed delegate — its degraded path's fresh-run options (a fresh single-pass review, the harness's own reviewer command) are skipped as they would spawn one — so it grades in-session, recording the in-session grading context, and the sink discloses the round as not covered by mutation detection; when a ticket can be issued, any fresh run the degraded path offers is itself ticketed, under a new role (`<role>-fresh`) so it is not counted as a re-spawn of the failed role
- WHEN the delegate is briefed, THEN it is told to compute the change diff read-only in the main tree (the snapshot may lack the base ref), to read change artifacts (`.prospec/`, which the snapshot does not hold) from the main tree read-only, to run every test, pin, and repro inside the printed snapshot path, to make ignored dependencies available there per the project test runner without writing the main tree (and, when that is impossible, to report the untested claim instead of running it in the main tree), and never to write refs, the stash, or the config, nor to run a fetch that writes `.git` metadata (`--depth`, `--shallow-*`, `--unshallow`)
- WHEN the reference states what it guarantees, THEN it claims detection and preservation only — never prevention or restoration — and states its threat model: an accidental or buggy delegate, not a malicious one; and it discloses what is not seen: ignored files (an ignored `prospec-report.json` included, as in a project that ignores the report `prospec check` writes); artifacts under `.prospec/` (tickets and checkpoints included) and a delegate that edits its own ticket or another CLI record there (a forged record can make a receipt pass); the main repository's `.git/config`, hooks and `info/exclude` (a hook or command a delegate sets there, such as `core.fsmonitor` or a reference-transaction hook, runs in the CLI's own receive git calls and in every later git call); repository metadata under `.git` that no facet reads (`.git/shallow`, `info/grafts`, `info/attributes`); a process that outlives its delegate (one still running after `--spawn-failed` or after a newer attempt superseded it, or a background process it started, which can change the tree after the receipt); a change recovered before receipt; content outside the project; pushes to any remote (remote-tracking refs are not a facet) — while stating that tags a `git fetch` auto-follows do change the refs facet, so a delegate's fetch can refuse an otherwise clean receipt; and delegations of several changes running concurrently in one repository, which are not isolated from one another (the facets span the whole repository, and a sibling worktree's commit or stash during a delegation refuses the receipt)
