### US-47: Trustworthy Escalation Decisions and Scoped Retry Authorization [P0]

As a developer using Prospec,
I want CLI-owned escalation decisions, durable history and event-bound retry authorization,
so that retries preserve human control and partial writes remain auditable and safely repairable.

**Acceptance Scenarios:**
- WHEN a station reaches a retry bound, THEN the CLI supplies the trigger, lifetime ordinal, allowed exits and one recommendation; read-only status preserves the recorded history.
- WHEN a pending event has lifetime ordinal at least two, THEN a new attempt needs a reasoned, unused grant for that event and station; replay consumes no grant and failed tests remain independently blocking.
- WHEN persistence only partly succeeds, THEN the result distinguishes recorded state from unpersisted observations, retains concurrent edits and permits only receipt-bound repair.
- WHEN a later verdict passes or the change is archived, THEN override reasons, event bindings and usage remain visible.

#### REQ-TYPES-110: Structured Escalation Decisions
Define additive escalation decision and ledger-record contracts shared by every consumer.
- WHEN a retry escalation is presented, THEN the decision contains trigger, event_id, station, lifetime ordinal, stable exits and exactly one recommended exit id belonging to those exits
- WHEN ordinal is at least two, THEN exits are re-scope, abandon and break-glass and the recommendation is re-scope, before trigger-specific rules
- WHEN a first escalation is oscillation or fix_induced_threshold_exceeded, THEN the recommendation is revert-and-redesign and no ordinary retry exit is offered
- WHEN a first escalation has another supported trigger, THEN manual-intervention is recommended with actionable cause-specific remediation
- WHEN existing consumers read EscalationReport, THEN type, message, diagnostics and tradeoffOptions remain available; decision is additive and tradeoffOptions projects the same allowed exits
- WHEN legacy history is incomplete, THEN its conservative count and completeness limitation are disclosed without inventing missing triggers

- WHEN an observed escalation cannot be persisted, THEN the failure separates persisted history from observed_escalation with persisted false and null event_id/ordinal; the emitted decision uses the persisted lifetime count (zero is allowed on this failure path) and does not claim an actionable grant target for that observation
- WHEN the failed-write projection has zero or one persisted event, THEN it applies first-trigger policy without incrementing the persisted ordinal; with at least two persisted events, including resolved history, it offers only re-scope, abandon and break-glass and recommends re-scope; any existing pending event is separately identified
- WHEN a write partially succeeds, THEN the typed outcome reports actual event, metrics, artifact, accepted and grant persistence plus the original failure cause, and text and JSON render the same decision


#### REQ-LIB-098: Chronological Escalation History and Attempt Identity
A shared pure reducer derives escalation history, pending state and grants from quality_log, which is the sole persistent ledger.
- WHEN a new review round trips or a new accepted planning or verify attempt reaches or remains beyond the retry bound, THEN its unique event is appended and lifetime ordinal advances across stations and review loops
- WHEN an event, identical accepted outcome with unchanged causal inputs, failed test attempt, status query or refused attempt is replayed, THEN ordinal does not advance; event identity and accepted attempt identity are separate, so a changed same-round outcome still undergoes admission
- WHEN a same review round trips again after resolution, THEN a trigger transition reopens that event without increasing its lifetime ordinal; unchanged pending replay adds no transition
- WHEN planning identity is computed, THEN validated report, applicable artifacts, acceptance and full-plan candidate/decision semantics including recommendation participate, while sign-off graded_by does not
- WHEN verify identity is computed, THEN its complete grade-affecting outcome including merged warnings, effective dimensions and applicability participates together with actual proposal, delta-spec, effective acceptance, tasks/check/test inputs and any context; absence of context_id does not omit causal specification inputs, and a warning-driven grade change is a new attempt
- WHEN a current event is resolved, THEN pending is cleared while lifetime history remains; a later escalation obtains the next ordinal and cannot reuse an earlier grant
- WHEN a dedicated trigger, override, consume or resolve entry is written, THEN it cannot count as a review close, round counts entry, verifier verdict or plan sign-off
- WHEN recognizable legacy breaker warnings and structured entries share a provable anchor, THEN they count once; missing historical HALTs are not reconstructed
- WHEN a reasoned override is granted, THEN it is bound to the current event and station and permits one new accepted attempt; replay does not consume it

- WHEN mixed legacy and structured history is projected, THEN recognizable events are processed in original log order, deduplicated only by provable shared anchors, and incomplete historical coverage remains disclosed after new structured events arrive
- WHEN a new verdict would hide a recognizable legacy retry tail, THEN its source anchor is materialized in the same metadata commit before accepting the new verdict; status itself remains read-only
- WHEN status, any admission sink or provenance reader evaluates retry history, THEN it uses the same explicitly resolved maxStationRetries rather than a helper-specific default
- WHEN attempt identity is computed, THEN report path, date and output artifact bytes are excluded, while actual decision inputs participate; review stores its causal base receipt so its own writes cannot fabricate a new attempt, and an older accepted replay never replaces a newer verdict


#### REQ-SERVICES-126: Event-Bound Admission and Single-Use Grants
The existing review merge, planning verifier-report log and verify record services enforce shared escalation admission before new attempt writes.
- WHEN pending ordinal is at least two and no current-event/current-station unused grant applies, THEN every new attempt at the three sinks is refused non-zero with the current decision and remediation before verdict or findings writes
- WHEN change log receives Manual override: with a blank suffix, THEN it refuses; a nonempty reason for the pending station is bound by the CLI to the current event without an additional required flag
- WHEN a new attempt is accepted under a grant, THEN consumption and the accepted outcome are committed in the same atomic metadata write; pre-commit validation or I/O failure does not consume it
- WHEN fresh-test or live-evidence gates refuse, THEN an override does not authorize known-red, missing, stale, running or unprovable evidence
- WHEN review has a persistent observed failure, THEN truthful failure events and the existing metrics-only splice may persist without findings, a completed review round or grant consumption, and partial writes are reported
- WHEN an identical accepted outcome with unchanged causal inputs is replayed, THEN existing independent gates still apply and unchanged metadata stays byte-identical; missing evidence can be repaired for that accepted identity without another consumption; a shared review round number alone does not prove replay
- WHEN re-scope is described, THEN remediation uses human scope edits and supported reason/digest amendments or a new Story, preserves forward-only and terminal-state refusals, and does not automatically unlock the current event
- WHEN status, verify or archive presents results, THEN lifetime override count, reasons, bound event and usage remain visible after later PASS entries

- WHEN a verifier report contains a warning beginning with Manual override:, THEN it remains report provenance and never creates a grant; only the explicit composed WARN path can mint a reasoned current-event/current-station grant
- WHEN accepted review persistence writes review.md but the subsequent metadata write fails, THEN the artifact receipt identifies the incomplete attempt and no acceptance or consumption is claimed; retry repairs metadata only while its causal receipt and applicable authorization remain valid, preserving newer artifacts
- WHEN verify metadata commits but evidence persistence fails, THEN acceptance and consumption remain committed; identical retry repairs only missing evidence for that attempt without changing a newer verdict or consuming again
- WHEN a cross-file await completes, THEN the next target bytes and relevant live inputs are rechecked before writing; concurrent content and successful prior writes are preserved, with no cross-file rollback claim
- WHEN persistent-test event persistence fails, THEN metadata and review remain byte-identical, no metrics write follows, and the typed refusal applies REQ-TYPES-110 to pre-write persisted history plus the unpersisted observation
- WHEN persistent-test event persistence succeeds but review bytes change before the metrics splice, THEN the event remains recorded, concurrent review content is retained, and the failure reports event persisted and metrics uncommitted; retry of the same observed attempt deduplicates the event


#### REQ-TEMPLATES-244: CLI-Owned Escalation Guidance
Execution guidance echoes the CLI escalation policy and preserves human ownership of exceptional authorization.
- WHEN plan, tasks, review, verify or fast-forward reaches escalation, THEN it echoes the CLI exits and unique recommendation without composing alternatives or disguising another round as manual intervention
- WHEN break-glass is an allowed exit, THEN a grant requires the human's explicit nonempty rationale; an agent does not self-authorize
- WHEN circuit-breaker, cascade, metadata or lifecycle references explain escalation, THEN they point to CLI-owned events, replay, single-use grants and actual supported remedies using host-neutral terminology
- WHEN archive guidance presents a completed change, THEN it includes durable override history and does not discard it because a later verdict passed
- WHEN public CLI documentation and generated skills are updated, THEN bilingual documentation, template sources, bundled templates and deployed instructions agree on the supported flags and policy

- WHEN durable history is inserted or refreshed in verify or archive output, THEN only its owned block outside Markdown fences is changed, adjacent authored prose and fenced examples remain byte-identical, duplicate archive copies agree and re-running is idempotent


#### REQ-TESTS-130: Escalation Counterexamples Across Four Layers
Tests distinguish event policy, admission, replay and durable presentation from the previous permissive behavior.
- WHEN the policy matrix runs, THEN first and repeated events of every supported trigger have the prescribed exits and a recommendation within the set
- WHEN cross-station, loop, replay, grant, legacy and resolution fixtures run, THEN they assert lifetime ordinals, current pending state, single-use consumption and completeness
- WHEN three-sink refusals and partial-write fixtures run, THEN they assert exit codes and exact artifact bytes rather than only error strings
- WHEN fresh-test and amendment counterexamples run, THEN reasoned grants cannot permit red evidence or regress lifecycle status
- WHEN text, JSON, later-PASS history and template contracts run, THEN they assert the same decisions, durable reasons and CLI-owned choices
- WHEN repository CI parity checks run, THEN lint, typecheck, test coverage, factual counts, agents, knowledge and strict drift checks pass with coverage at least 80 percent

- WHEN R330-1 through R330-8 regressions run, THEN they cover report-warning grant spoofing, fenced-history preservation, custom retry configuration, legacy-tail preservation, event-to-metrics concurrent edits, no-context verify specification changes, chronological mixed history, and persisted-versus-observed failure policy
- WHEN event-write failures are exercised, THEN the zero/one/two persisted-event matrix and applicable pending/resolved combinations assert text and JSON, original cause, exact metadata/review bytes, truthful ordinals and no fictitious consumption
- WHEN each sink write boundary is fault-injected, THEN tests distinguish untouched, artifact-only, metadata-only and complete outcomes, safe repair and old-replay protection rather than merely asserting error strings
