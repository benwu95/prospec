# SDD Workflow — Formal Abandonment and Retry History

## US-49: Preserve an Abandoned Attempt and Explain a Retry [P0]

As a developer using Prospec,
I want to end an unsuccessful change while preserving its reasons and uncommitted work,
so that a later attempt can inspect the evidence and explain what has changed.

**Acceptance Scenarios:**
- WHEN I abandon a change with a nonblank reason, THEN its artifacts move to `.prospec/abandoned/YYYY-MM-DD-name/` with reason, observed escalation and declared overturned Premise fields, without spec-sync or trust-zone writes.
- WHEN abandonment completes, THEN normal status omits the attempt from active work while JSON exposes its history.
- WHEN the command succeeds, THEN it prints a local tracker summary and preservation paths without sending a tracker request.
- WHEN project-scoped work is uncommitted, THEN preservation keeps staged and unstaged edits plus nonignored untracked content before moving artifacts, without restoring user files or changing Git index, HEAD or refs.
- WHEN preservation, path validation or destination admission fails, THEN the command retains the source and reports the failure and any preserved data; partial publication reports the actual remaining locations.
- WHEN a successful archive has the same date/name, THEN it remains independent of the abandoned destination; history readers use only the abandoned root, distinguishing missing roots from unsafe roots and broken linkages.
- WHEN a downstream project is nested in a monorepo or relocates its trust zone, THEN abandoned storage remains at that Prospec project root; language policy includes the root while daily language sampling excludes historical content.
- WHEN a new story uses the same whitespace-normalized nonempty issue, THEN it lists the matched abandoned reasons and stores their identities and digests without guessing tracker equivalence.
- WHEN a linked retry lacks a substantive difference, THEN every scale and direct forward writer remains blocked; completing the difference restores its applicable workflow without claiming the difference is true.
- WHEN no history matches or an existing change has no retry declaration, THEN its applicable legacy or sourced-premise behavior remains.

#### REQ-TYPES-112: Abandonment and retry linkage contracts
The change contract includes the gate-owned terminal status abandoned and optional abandonment/retry linkage records. Existing metadata without retry linkage remains readable.
- WHEN abandonment completes, THEN its record includes a nonempty reason, timestamp, original status, the latest observed escalation trigger/ordinal or explicit absence, declared overturned Premise leaf values and the preservation manifest location.
- WHEN a new change is created, THEN retry_of records the creation-time matching abandoned entry IDs (the existing `archive` key is relative to `.prospec/abandoned/`, not `.prospec/archive/`) and metadata digests, including an empty list when there are none; absent linkage identifies the compatible legacy contract.
- WHEN generic status mutation is requested, THEN it cannot set abandoned or reactivate an abandoned change.

#### REQ-LIB-100: Project-scoped uncommitted work preservation
The preservation helper saves project-scoped uncommitted inputs before change artifacts move, using read-only Git commands and byte-preserving files.
- WHEN tracked changes exist, THEN separate HEAD-to-index and index-to-worktree binary/full-index patches preserve staged and unstaged edits even when their net HEAD diff is empty.
- WHEN changed regular or nonignored untracked files, symlinks or deletions exist, THEN the manifest records file bytes/hash/mode, symlink targets or deletion identities; the project root and Git prefix identify the scope and exclude monorepo siblings.
- WHEN preservation enumerates inputs, THEN existing project .prospec content follows the same tracked/nonignored policy; only the operation's own destination is excluded to prevent recursive capture.
- WHEN Git is unavailable, HEAD is unborn, inputs conflict, or sparse/skip-worktree, assume-unchanged, gitlink, unsafe paths or unreadable inputs prevent complete capture, THEN preservation refuses before moving source artifacts.
- WHEN capture completes, THEN saved bytes are read back and input paths/content/modes, source artifacts and Git facets are rechecked before publication; detected changes refuse publication.
- WHEN preservation runs, THEN it does not restore or delete user work files or write the Git index, HEAD or refs; external diff and textconv commands are disabled.

#### REQ-SERVICES-128: Formal abandon publication
The abandon service requires a nonblank reason, preserves uncommitted work, then moves the change to a collision-free date/name entry under .prospec/abandoned and publishes abandoned metadata last. It does not run spec-sync, finalize, tracker requests or trust-zone writers. Successful archives remain under `.prospec/archive/`; a same-named entry there is not an abandonment collision.
- WHEN the change is already terminal, the destination exists, reserved artifact names collide, or latest delegation tickets remain open/refused, THEN the command refuses before moving source artifacts and names the remedy.
- WHEN overturned fields are supplied, THEN each must be an existing scalar leaf of the structured Premise and its original value is retained; omitted fields and absent escalation are reported without inferred claims.
- WHEN preservation or preflight fails, THEN the original change remains intact and any partial preservation location is reported.
- WHEN moving artifacts or final metadata publication fails, THEN the command reports the actual source/abandoned/preservation paths, phase and moved/pending artifacts; the incomplete entry is not completed abandoned history and retry refuses its collision until the user has inspected and repaired it.
- WHEN final metadata publication succeeds, THEN the change is terminal abandoned, its original proposal and other artifacts remain available and the preserved work is not automatically restored.

#### REQ-LIB-101: Completed abandoned history and fixed retry admission
One contained reader rooted exclusively at `.prospec/abandoned/` identifies completed abandoned attempts by validated terminal metadata and preservation manifest; operation-marked entries without a completed record are reported as incomplete. An absent abandoned root is empty history; an unreadable or unsafe root is an error. Successful archive contents never supply abandoned history; no fallback reader or automatic migration is introduced.
- WHEN an incomplete operation identifies a source change that remains active, THEN status reports that source as blocked and forward admission refuses it until the partial publication is inspected and repaired.
- WHEN story receives a nonempty issue, THEN all completed abandoned records whose issue matches normalizeIssueRef are returned with their reasons; matching collapses whitespace only and never infers URL or tracker-ID equivalence.
- WHEN issue is absent or no records match, THEN no retry history is linked and the applicable existing Premise behavior remains.
- WHEN a new retry is assessed at any scale, THEN linked abandoned entry identities/digests must remain valid and a substantive retry_difference narrative must cover the captured history set before existing scale exemptions are considered.
- WHEN a linked record is missing, corrupt or changed, or difference is blank/placeholder, THEN assessment blocks; completing the narrative restores the applicable route without claiming its truth or guaranteeing success.
- WHEN later abandoned records appear, THEN they do not silently alter the creation-time linked set; absent retry_of on an existing change remains compatible.

#### REQ-CLI-061: Abandon command and local tracker summary
The CLI exposes change abandon <name> --reason <text> with repeatable --overturned <field>, delegating to the abandon service and presenting its typed result.
- WHEN abandonment succeeds, THEN human output provides a pasteable tracker summary and abandoned/preservation paths (existing JSON `archiveDir` keys contain the actual abandoned destination) without sending a tracker request.
- WHEN JSON output is requested, THEN it emits the structured service result; terminal human output sanitizes untrusted reason and path text.
- WHEN abandonment fails, THEN output preserves the service's actionable phase and path details and exits unsuccessfully.

#### REQ-TEMPLATES-246: Abandon and retry workflow guidance
Shipped workflow guidance describes the formal abandon exit, preservation boundary and retry handoff through the CLI-owned contracts, distinguishing `.prospec/abandoned/` from successful `.prospec/archive/` in downstream projects as well.
- WHEN a human chooses abandonment, THEN guidance invokes change abandon with their reason, preserves artifacts and reports paths; restoration remains a separate human decision.
- WHEN story or fast-forward handles a linked retry, THEN it reviews prior reasons and authors retry_difference before applicable progression, including light scales, while preserving source identity.
- WHEN guidance describes failure, THEN it distinguishes untouched-source preservation failure from partial publication and directs inspection of reported paths before retry.

#### REQ-TESTS-132: Abandon and retry regression matrix
Unit, contract, integration and CLI tests verify abandonment and retry behavior against real temporary Git repositories where Git state matters.
- WHEN preservation tests run, THEN staged/unstaged cancellation, binary content, deletions, symlinks, untracked/ignored inputs and monorepo scope retain their expected bytes and boundaries.
- WHEN failure tests run, THEN collision, unsupported Git states, read/copy/publication failures, unsafe paths and detected concurrent changes retain inspectable artifacts and never claim a successful abandoned record prematurely.
- WHEN retry tests run, THEN same/different/absent issue, whitespace normalization, legacy compatibility, every scale, corrupt linkage and direct forward writers share the admission result.
- WHEN directory isolation tests run, THEN same-named successful/abandoned entries coexist, archived corruption cannot supply or block abandoned history, absent/unsafe roots differ, linked abandoned inputs are rechecked, and relocated base_dir/monorepo cases remain scoped to the Prospec project root.
- WHEN lifecycle tests run, THEN history is queryable, human active lists exclude completed abandonment, successful archive remains gated and both learn yield corpus paths exclude abandoned/incomplete attempts.
