## US-42: One Adjudicator per Change, One Route per Station [P1]

As a developer running several changes at once and as the agent that routes between stations,
I want each local gate adjudicated from the target change's own facts, a failed re-verify routed straight back to verify, and every planning verdict recorded through one validating sink,
so that another change's missing evidence never blocks mine and no station has to be reached before its real blocker is known.

**Acceptance Scenarios:**
- WHEN one change holds current review and test evidence while a sibling holds none, THEN the gates refuse only the sibling, and the repository-wide check still reports it
- WHEN a change re-verified to grade B, C or D still carries `status: verified`, THEN routing sends it back to verify with a stable reason code rather than on to archive
- WHEN a planning verifier verdict is recorded, THEN it passes an executable schema, a `FLAWS` verdict lands as a gate `FAIL`, and the entry is stamped so a station's own gate note is never mistaken for it
- WHEN the transition rules are read, THEN one executable router owns them and the rendered station guidance names the same next stations it computes

**Independent Test:**
Build a real-Git fixture with two verified changes, one with evidence and one without: archive and verify refuse only the second while the repository check still reports it; re-verify the first to grade C and assert routing returns it to verify with `VERIFY_GRADE_BELOW_BAR`; record a `FLAWS` verifier report and assert the entry reads `result: FAIL` and routing returns the change to its station.

### Behavior Specifications

#### REQ-TYPES-096: Planning verifier report contract
`types/station.ts` exports the planning-verifier contract: `PLANNING_VERDICTS = ['PASS','WARN','FLAWS']`, `PLAN_VERIFIER_DIMENSIONS` (project_layering, blast_radius, state_safety, delta_spec, reuse), `TASKS_VERIFIER_DIMENSIONS` (bidirectional_coverage, dag_topological_order, tdd_module_closure, task_sizing_schema), the strict `PlanVerifierReportSchema` / `TasksVerifierReportSchema` (`verdict`, `dimensions` with exactly the owning key set and `{result, rationale}` values, required `evidence`, optional `warnings`; no additional keys at any level), `VERIFIER_REPORT_SCHEMAS` keyed by station skill (`prospec-plan`, `prospec-tasks`), and `planningVerdictToGateResult` (`PASS`→`PASS`, `WARN`→`WARN`, `FLAWS`→`FAIL`).
- WHEN a payload carries a verdict outside `PLANNING_VERDICTS`, a dimension outside the owning key set, a missing required field, or an additional key, THEN the schema rejects it naming the field path
- WHEN a verdict string differs only by case or surrounding whitespace (`flaws`, ` FLAWS `), THEN it is rejected — no lenient normalization
- WHEN the rubric references or the station skills render the verdict or dimension vocabulary, THEN the text is projected from these constants through the render context, never hand-written
- WHEN a `rationale` or a `warnings[]` item is multi-line or exceeds the relayed `summary` ceiling, THEN the schema rejects it (`relayedString` — these strings are appended to `quality_log.warnings` and printed by `prospec status` as raw lines)

#### REQ-LIB-077: Per-change check adjudication
`lib/change-gate.ts` exposes the pure, I/O-free `adjudicateChangeCheck(report, checkId, changeName)` returning `{ status, reason?, findings }` where `status` ∈ `pass` | `warn` | `fail` | `skipped` | `unprovable`.
- WHEN the check is `repository`-scoped in `DRIFT_CHECK_SCOPES`, THEN the verdict is the check's own report status
- WHEN the check is `change`-scoped and its report entry is absent, carries no `subjects`, or its `subjects` does not list the target, THEN the verdict is `unprovable` with a reason naming which of the three holds — never a vacuous pass
- WHEN the check is `change`-scoped and `skipped`, THEN the verdict is `skipped` carrying the check's own reason verbatim — evaluated before the `subjects` membership test, since a skipped check graded nobody and which skips a gate accepts is that gate's policy
- WHEN the check is `change`-scoped and the target is listed under `subject_skips`, THEN the verdict is `skipped` with that reason — evaluated after the subjects test and before the finding filter, so a target the evaluator could not grade never passes on the absence of its own findings
- WHEN the check is `change`-scoped and the target is enumerated, THEN only findings whose `source_path` lies under `.prospec/changes/<changeName>/` decide the verdict (`fail` on any fail-severity finding, `warn` on any other finding, else `pass`); a finding of that check anchored outside every `.prospec/changes/` directory is attributed to the target (fail-closed), never dropped
- WHEN a sibling change carries findings of the same check, THEN they do not affect the target's verdict

#### REQ-SERVICES-109: change log records a planning verifier report
`change-log.service.execute` accepts `verifierReport` (`{ skill, path, date? }`) as an alternative to a caller-composed `entry`: it reads the file (path resolved against `cwd`), validates it against `VERIFIER_REPORT_SCHEMAS[skill]`, derives `result` through `planningVerdictToGateResult` and `warnings` from the payload's `warnings` plus one `"<dimension>: <rationale>"` string per non-PASS dimension, then appends through `lib/change-metadata.appendQualityLogEntry`.
- WHEN the file is missing, not JSON, or fails the skill's schema, THEN the service throws `PrerequisiteError` naming the failing field path and writes nothing
- WHEN the skill has no entry in `VERIFIER_REPORT_SCHEMAS`, THEN the service refuses before reading the file
- WHEN the payload verdict is `FLAWS`, THEN the appended entry's `result` is `FAIL`; `WARN` and `PASS` map to themselves
- WHEN the entry is appended, THEN it carries `verifier_verdict` (the payload verdict) as the provenance stamp only this sink writes, and its file path is resolved against the service's `cwd`
- WHEN both `verifierReport` and a composed `entry` are supplied, THEN the service refuses — one run has one verdict source; a composed `entry` carrying `verifier_verdict` is likewise refused, so the stamp is written only from a validated report

#### REQ-CLI-053: change log --verifier-report and status reason codes
`prospec change log --skill <station> --verifier-report <file>` records a planning verifier payload; `--result` is required only when `--verifier-report` is absent.
- WHEN `--verifier-report` is combined with `--result`, `--warning`, `--grade`, `--dimension`, `--criticals-found`, `--criticals-fixed` or `--majors`, THEN commander renders a usage error (`Option.conflicts()`), and the service refuses the same combination for programmatic callers
- WHEN neither `--result` nor `--verifier-report` is given, THEN the command exits 1 naming both forms
- WHEN a `FLAWS` payload is recorded, THEN the command exits 0 and the appended entry reads `result: FAIL`; WHEN the payload fails the schema, THEN it exits 1 with the field path on stderr and the file unchanged
- WHEN `prospec status` prints a change, THEN each `reason:` line is prefixed with the route's `[CODE]`, and `--json` carries `code`

#### REQ-TEMPLATES-228: One verdict vocabulary and one station route across skills
`agent sync` injects `planning_verdicts`, `plan_verifier_dimensions`, `tasks_verifier_dimensions` (projected from `types/station.ts`) and `break_glass_prefix` (`BREAK_GLASS_PREFIX` from `types/status.ts`) into the skill render context; `plan-verifier-rubric`, `tasks-verifier-rubric`, `prospec-plan`, `prospec-tasks` and `prospec-ff` render the vocabulary from those variables.
- WHEN the rendered skill and reference set is scanned, THEN no template carries the singular `FLAW` verdict, and every verdict/dimension list equals the schema constants' projection
- WHEN `prospec-ff` Phase 2 runs its INVEST check, THEN it records concerns via `prospec change log --result WARN` and does not hard-block — the same advisory contract as `prospec-new-story` and `cascade-protocol`
- WHEN `prospec-ff` reaches Phase 3 or 4, THEN it enters the `prospec-plan` / `prospec-tasks` station skill (reload per the Station Transition Protocol), records the verifier report through `prospec change log --skill <station> --verifier-report <file>`, and lets `prospec status` decide the next station; a recorded FAIL routes back to that station unless a Break-Glass `--result WARN --warning "Manual override: …"` supersedes it
- WHEN the `cascade-protocol` Station Transition Gates table is rendered, THEN every row's current and next station is a member of `SDD_STATIONS`, the table carries `design` (ui_scope full/partial, between plan and tasks) and `promote` (backfill entry landing at implemented → review) rows, and no `awaiting_signoff` pseudo-station appears — sign-off lives in the Tastemaker section
- WHEN a `scale: backfill` trajectory is described, THEN it reads `promote → review → verify → knowledge-update → Tastemaker sign-off`, never plan or tasks

#### REQ-TESTS-113: Per-change gate, routing and vocabulary regression coverage
The suite pins the per-change gate, the failed re-verify route, the verifier sink and the single verdict vocabulary.
- WHEN a real-Git fixture holds change A (verified, current review/test evidence) and change B (verified, no evidence), THEN `archive a --dry-run` refuses nothing for A, `archive b` is refused with a `REVIEW_STALE`-class reason, and `prospec check` still reports B's findings
- WHEN A is re-verified to grade C, THEN `prospec status` routes A to `verify` with code `VERIFY_GRADE_BELOW_BAR`
- WHEN the contract suite runs, THEN every `DRIFT_CHECK_IDS` member has a scope in `DRIFT_CHECK_SCOPES`, every change-scoped evaluator emits `subjects` and anchors its findings under `.prospec/changes/<name>/`, the rendered rubric vocabulary equals the schema constants, no rendered template contains `FLAW\b`, and `src/` contains no `evaluateCascadeTransition`
- WHEN the route-parity contract runs, THEN for every row of the rendered `cascade-protocol` Station Transition Gates table the set of next stations named in the row equals the set `routeChange` returns for that current station across scale ∈ {quick, standard, full, backfill} × ui_scope ∈ {null, full, none} with a passing verifier verdict — cell by cell, not merely membership in `SDD_STATIONS`
- WHEN the unit suite runs, THEN `routeChange` is exercised over verified × {S, A, B, C, D, null} × knowledge-sync and over plan/tasks × latest verifier FAIL, and `change log` with a verifier report covers PASS, WARN, FLAWS, unknown enum, missing field, extra key, and an unregistered skill
- WHEN compatibility regressions run, THEN a proven backfill (no `tasks.md`) is not refused by `task-completion`, a `quick` change's skipped `delta-spec-provenance` does not block, `--allow-incomplete` exempts only the target's completeness, and a legacy report without `subjects` yields `CHECK_UNPROVABLE` rather than pass
