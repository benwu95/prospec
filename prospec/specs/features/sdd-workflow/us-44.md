### US-44: A Plan Can Pause for a Human Sign-off [P0]

As a maintainer steering a standard or full change locally,
I want a pause after the plan station — opted in by config, or by default when the AI proposed the problem — where I sign off on the audited plan (a full change's measured candidate recommendation, a standard change's direction summary) before any tasks are generated, while cloud and scheduled runs override the pause and stay autonomous,
so that I confirm the architectural direction at its cheapest point instead of discovering a wrong direction at the final Tastemaker gate and re-running implement, review and verify.

**Acceptance Scenarios:**
- WHEN `.prospec.yaml` sets `workflow.pause_at: [plan]` (or the change's verified Premise is `ai-proposed`), the change is `scale: standard` or `full` and the plan verifier recorded PASS/WARN with no counting sign-off, THEN `prospec status` reports `AWAITING_HUMAN_PLAN_SIGNOFF` with no next station, and plan and ff HALT to present the sign-off material for the change's scale
- WHEN the human records the sign-off with `prospec change log --skill prospec-plan --signoff <option>` (`plan` below full scale), THEN `prospec status` routes to tasks; a newer plan verifier entry or an edit to the signed plan version makes the change pause again
- WHEN `PROSPEC_PAUSE_AT` is set, THEN it alone decides for that run (empty or `none` = no pause), and an invalid value makes `prospec status` exit non-zero rather than silently not pausing
- WHEN no pause resolves, or the scale has no plan, THEN routing is exactly as before and the agent selects the candidate in-session without asking the human
- WHEN a change is archived, THEN its summary names the plan decision and whether a human signed it off

**Independent Test:**
Build router fixtures for pause + full, pause + standard, no pause, pause + quick/backfill and a signed-off plan; assert only the paused standard and full plans without a counting sign-off return `AWAITING_HUMAN_PLAN_SIGNOFF`, then drive pause → sign-off → tasks through the CLI for both scales.

#### REQ-TYPES-105: Opt-in pause configuration contract
The config schema carries an optional `workflow.pause_at` declared as unknown-shaped data, the types layer exports `PAUSE_STATIONS` (`plan` only) and `PAUSE_AT_ENV_VAR` (`PROSPEC_PAUSE_AT`), and `PauseAtInvalid` (`PAUSE_AT_INVALID`) is the error a malformed pause setting raises.
- WHEN `.prospec.yaml` omits `workflow.pause_at`, THEN the config parses exactly as before and contributes no pause station; whether a change pauses is resolved per REQ-LIB-086
- WHEN `workflow.pause_at` has any shape (array, scalar, object), THEN config parsing itself still succeeds, so a mistyped value can never turn the whole config into an unreadable one that silently disables the pause
- WHEN `PauseAtInvalid` is raised, THEN its message names the source (`PROSPEC_PAUSE_AT` or `.prospec.yaml workflow.pause_at`) and the offending value, and its suggestion lists the valid station names (the config form as a YAML list) and states that `PROSPEC_PAUSE_AT` set to `none` or empty disables pausing — only on the human's instruction

#### REQ-TYPES-106: Human-halt routing codes and pause facts
`WORKFLOW_REASON_CODES` appends `AWAITING_HUMAN_PLAN_SIGNOFF` and `PLAN_VERIFIER_PENDING` to its routing group and then `KNOWLEDGE_INPUT_INVALID`; the types layer exports `HUMAN_HALT_CODES` (`ESCALATE_TO_HUMAN`, `AWAITING_HUMAN_PLAN_SIGNOFF`, `KNOWLEDGE_INPUT_INVALID`) with `isHumanHaltCode()`, and `ChangeRouteFacts` carries `pauseAtPlan`, `planSignedOff` and `planChangedSinceVerifier`.
- WHEN `WORKFLOW_REASON_CODES` is read, THEN the two codes follow `ESCALATE_TO_HUMAN` in the routing group and every earlier code keeps its value (append-only; matched by value)
- WHEN `WORKFLOW_REASON_CODES` is read, THEN `KNOWLEDGE_INPUT_INVALID` follows `PLAN_VERIFIER_PENDING` as the last routing code, and `HUMAN_HALT_CODES` holds exactly `ESCALATE_TO_HUMAN`, `AWAITING_HUMAN_PLAN_SIGNOFF` and `KNOWLEDGE_INPUT_INVALID`
- WHEN a route has `next: null` on a non-archived change, THEN its `code` is a member of `HUMAN_HALT_CODES`, and the `next: SddStation | null` shape is unchanged for existing `--json` consumers
- WHEN `ChangeRouteFacts` is constructed, THEN `pauseAtPlan` states whether that change's resolved pause stations include `plan`; at `status: plan`, `planSignedOff` states whether the change holds a sign-off that counts per REQ-LIB-088 for its scale and current plan version, and `planChangedSinceVerifier` states whether the current plan version differs from the `audited_plan_digest` of the latest plan verifier report (false when that report carries none); none of them is display data

#### REQ-TYPES-107: Candidate and decision payload contracts
The station contracts define closed `CandidatePayloadSchema` and `DecisionPayloadSchema`, `DECISION_GRADED_BY` (`human`, `in-session`), and the `candidates` validate kind.
- WHEN a candidate payload is validated, THEN it is closed over `id`, `title`, `overview`, `trade_offs` (`pros`, `cons`, `blast_radius`), optional `call_chain`, optional `estimated_lines` and optional `touched_modules`
- WHEN a decision payload is validated, THEN it keeps `recommended_option`, the three-dimension closed `evaluation_matrix`, `rationale` and optional `hybrid_recommendation`, and additionally requires `graded_by`, a vocabulary distinct from the judgment-dimension `graded_by`
- WHEN `VALIDATE_KINDS` is read, THEN `candidates` is appended after the existing kinds

#### REQ-LIB-086: Pure pause-station resolver
`lib/config.ts` exposes `resolvePauseAt(config, env, options?)`, a pure resolver taking the environment as a parameter, where `PROSPEC_PAUSE_AT` takes precedence over an AI-proposed Premise, which takes precedence over `workflow.pause_at`.
- WHEN `PROSPEC_PAUSE_AT` is set (including the empty string), THEN it alone decides and neither the Premise option nor the config value is read; an empty or whitespace-only value, or `none` (`PAUSE_AT_NONE`, the portable form because Windows shells unset an empty variable), resolves to no pause stations
- WHEN `PROSPEC_PAUSE_AT` is unset and `options.aiProposedPremise` is true, THEN the result includes `plan` whatever `workflow.pause_at` holds, while an invalid `workflow.pause_at` still throws
- WHEN `PROSPEC_PAUSE_AT` is unset and the Premise option is absent or false, THEN `workflow.pause_at` decides, and an absent value or absent config resolves to no pause stations
- WHEN either source is comma-separated, THEN entries are trimmed, empty entries dropped and duplicates removed
- WHEN either source holds a non-string, a non-array config value, or a name outside `PAUSE_STATIONS`, THEN it throws `PauseAtInvalid` rather than ignoring the value
- WHEN `isAiProposedPremise(assessment)` (`lib/premise.ts`) is asked, THEN it is true only for a `ready` assessment whose Premise `source` is `ai-proposed`; legacy, exempt and blocked assessments never infer a source

#### REQ-LIB-087: Router opt-in plan sign-off branch
At `status: plan`, `routeChange` evaluates the pause after the verifier-FAIL branches and before the design insertion, for any scale whose artifact contract includes `plan.md` (decided from the scale registry, as design is) when `pauseAtPlan` is true.
- WHEN the latest plan verifier result is FAIL, THEN `PLAN_VERIFIER_FAILED` or `ESCALATE_TO_HUMAN` routes exactly as before, regardless of the pause
- WHEN the pause applies and no plan verifier result is recorded, THEN next is `plan` with code `PLAN_VERIFIER_PENDING` and a gate naming the verifier-report sink
- WHEN the pause applies, a PASS/WARN verifier result is recorded, `planSignedOff` is false and `planChangedSinceVerifier` is true, THEN next is `plan` with code `PLAN_VERIFIER_PENDING` and a reason stating that the plan changed after the verifier audited it, so the human is never asked to sign a version the sign-off would refuse
- WHEN the pause applies, a PASS/WARN verifier result is recorded and both `planSignedOff` and `planChangedSinceVerifier` are false, THEN next is `null` with code `AWAITING_HUMAN_PLAN_SIGNOFF`; the gate names `prospec change log --skill prospec-plan --signoff <option>` for `scale: full` and `--signoff plan` otherwise
- WHEN `planSignedOff` is true, `pauseAtPlan` is false, or the scale's contract has no `plan.md`, THEN routing continues to the design insertion and tasks exactly as before
- WHEN the pause branch is taken, THEN no retry streak is counted or reset by it

#### REQ-LIB-088: Single plan-verifier provenance rule and sign-off freshness
`lib/change-metadata.ts` exposes `verifierGateResultOf(entry)` as the one per-entry plan/tasks verifier provenance rule, plus `hasPlanSignoffAfterVerifier(qualityLog, history?, current?)` and `isPlanSignoffEntry(entry)`; `lib/escalation.ts` owns `planVersionDigest(plan, deltaSpec)`, the one plan-version identity the verifier stamp, the sign-off and the freshness check share.
- WHEN an entry carries a valid verifier_verdict stamp, THEN verifierGateResultOf returns its gate result; a legacy Break-Glass WARN qualifies only with a nonempty reason, and latest-result/streak/sign-off readers apply the shared pending policy before using that legacy bypass; structured grant records are not verifier results and cannot reset FLAWS streaks
- WHEN the latest plan verifier result is PASS or WARN and a later-positioned `prospec-plan` entry carries `signoff_option`, THEN the sign-off is positionally fresh; freshness is judged by quality_log position, never by the day-granular `date`
- WHEN a newer plan verifier entry follows the sign-off, or no verifier result precedes it, THEN the sign-off does not count
- WHEN `current` is given and the sign-off carries `signoff_plan_digest` different from `current.digest`, or `current.scale` is `full` and the sign-off option is `plan`, THEN the sign-off does not count; a sign-off without a digest is judged by position alone, and only while the latest plan verifier report carries no `audited_plan_digest`
- WHEN an entry carrying `signoff_option` or `signoff_plan_digest` is serialized, THEN the canonical key order keeps both stamps, so an appended sign-off is never silently dropped

#### REQ-LIB-089: Candidate mechanical metrics
`lib/artifact-validators.ts` exposes a pure `validateCandidates` that validates candidate and decision payloads and computes per-candidate metrics from injected dependency rules and an injected path-to-module attributor, both derived from `module-map.yaml` by their existing owners.
- WHEN a `call_chain` hop is resolved, THEN its first whitespace-delimited token containing `/` or `\` (other than a route beginning with `/`, which is an entry label) is the path token and — stripped of markdown quoting, a leading `./` and trailing punctuation, with `..` segments resolved — is attributed as a repo-relative path by the injected attributor (no directory-layout assumption is added; a token escaping the repository root is unattributable); a hop with no path token resolves only when its first token equals a module name, and is otherwise an entry label that is ignored; a path token the attributor cannot place is listed in `unknown_references`; hops are split on `→` or `->`
- WHEN two literally adjacent hops are both resolved and belong to different modules (an unresolved or label hop between them breaks the edge) and the callee is not in the caller's direct `depends_on`, THEN that directed edge is a violation; `direction_violations` counts distinct violating edges and `violating_edges` lists them
- WHEN `touched_modules_count` is computed, THEN it is the size of the declared `touched_modules` known to the map united with the modules resolved from `call_chain`; `estimated_lines` passes through or is null
- WHEN a candidate file is unreadable, schema-invalid or its file name disagrees with its `id`, no candidate is valid, or a present decision file is schema-invalid, THEN the verdict FAILs; violations, unknown references and a single valid candidate (degraded) are INFO
- WHEN a schema-valid decision names a `recommended_option` or a non-`tie` `evaluation_matrix` winner that is not a valid candidate, or recommends `hybrid` without a non-empty `hybrid_recommendation` or over fewer than two valid candidates, THEN the verdict FAILs; this candidate-set verdict (without metrics) is the one the plan sign-off reuses

#### REQ-SERVICES-116: status service resolves the pause and fails closed
`status.service` accepts an injectable `env` (default `process.env`), validates the pause and escalation-category settings once outside the per-change loop, and fills `pauseAtPlan` and `planSignedOff` per change.
- WHEN the pause setting or `workflow.always_escalate` is invalid, THEN `execute` rejects with `PauseAtInvalid` or `AlwaysEscalateInvalid` before any route is produced — including when no change is in flight, ahead of the clean-state report — so `prospec status` (and `--json`) exits non-zero with no partial report
- WHEN `.prospec.yaml` fails validation in a field other than the pause setting, THEN `workflow.pause_at` is still read from the parsed YAML, so an unrelated schema error never silently disables a committed pause, and `workflow.always_escalate` is read and validated from it alike; a `.prospec.yaml` that exists but cannot be read or is not parseable YAML pauses at every pause station unless `PROSPEC_PAUSE_AT` is set, and the `AWAITING_HUMAN_PLAN_SIGNOFF` / `PLAN_VERIFIER_PENDING` route then carries a reason naming the file problem; an absent file has no pause setting
- WHEN a change is collected, THEN `pauseAtPlan` comes from `resolvePauseAt` with `aiProposedPremise` set by `isAiProposedPremise` on that change's Premise assessment, and at `status: plan` both `planSignedOff` and `planChangedSinceVerifier` are judged against the `planVersionDigest` of its current plan.md and delta-spec.md (with the change's scale for `planSignedOff`)
- WHEN a route is `AWAITING_HUMAN_PLAN_SIGNOFF`, THEN no nextSkill, skill path or reference map is attached, and its reasons name the resolved `always_escalate` categories and, when only the AI-proposed Premise caused the pause, that cause
- WHEN unresolved warnings are collected, THEN a plan sign-off entry is skipped so it never masks an earlier plan WARN
- WHEN the service runs, THEN the filesystem stays byte-identical

#### REQ-SERVICES-117: change log records a plan sign-off
`change-log.service` accepts a sign-off (`--signoff <option>`) as a verdict source exclusive of `--result` and `--verifier-report`, and writes it only after every refusal has passed; a `prospec-plan` verifier report entry is stamped `audited_plan_digest` from the plan.md and delta-spec.md bytes it captured.
- WHEN the skill is not `prospec-plan`, the option is outside the vocabulary, the change's scale has no plan, or the latest plan verifier result is not PASS/WARN, THEN it refuses and metadata (and any decision.json) stays byte-identical
- WHEN the option is `plan`, THEN it refuses for `scale: full` (which signs a candidate option) and otherwise reads no candidate files
- WHEN the option is a candidate option and `candidates/decision.json` is missing or schema-invalid, or the candidate set fails the `validate candidates` verdict (so a non-hybrid option always has a schema-valid `candidates/<option>.json`), THEN it refuses and both metadata and decision.json stay byte-identical
- WHEN the option is a candidate option and the latest plan verifier report entry (one carrying `verifier_verdict`; a later Break-Glass WARN audited nothing and is skipped) is absent (only a Break-Glass override is recorded) or has no `audited_option`, or an `audited_option` other than the option, THEN it refuses — stating which of the three holds — and names re-recording the plan verifier, so the recommended option cannot change after the audit; `change log --verifier-report` for `prospec-plan` stamps `audited_option` from a schema-valid decision.json
- WHEN the latest plan verifier report entry is absent, or its `audited_plan_digest` differs from the `planVersionDigest` of the current plan.md and delta-spec.md, THEN it refuses and names running the plan verifier on the current plan and recording its new report; a report recorded before the stamp existed carries none and is accepted by position, so an in-flight change is never stuck on a report it cannot re-stamp
- WHEN metadata.yaml, plan.md or delta-spec.md change between the reads the refusals judged and the write, THEN it refuses and writes nothing, so a concurrently recorded verifier entry is never overwritten
- WHEN the option differs from decision.json's `recommended_option`, THEN it refuses and names the re-selection path (revise plan.md, delta-spec.md and decision.json, re-record the plan verifier, then sign off), because plan.md and the verifier audited the recommended option
- WHEN a composed entry carries `signoff_option`, `signoff_plan_digest` or `audited_plan_digest`, THEN it is refused, because those stamps are written only by the sign-off and verifier paths
- WHEN a refusal leaves a paused change unable to sign off (no decision.json after a mid-flight `change scale full`, or a legacy decision.json without `graded_by`), THEN the message names the remedies for the change's scale — the text the router's AWAITING reason uses; at full scale: record the plan verifier report after decision.json is written (re-running the Phase 4 candidate selection first when there is none), add `graded_by` and re-record the plan verifier, or — only on the human's instruction — skip the pause for one run with `PROSPEC_PAUSE_AT` set to `none` or empty
- WHEN `--warning` accompanies `--signoff`, THEN the strings are stored as the human's notes on the PASS entry and never surface as unresolved warnings
- WHEN the sign-off is accepted, THEN a candidate option first rewrites decision.json atomically with only `graded_by` set to `human` (`recommended_option` unchanged), and a `prospec-plan` PASS entry carrying `signoff_option` and `signoff_plan_digest` is appended; a re-run after a partial failure is idempotent

#### REQ-SERVICES-118: validate candidates reads the change's candidate set
`prospec validate candidates` reads `candidates/option-*.json` and an optional `candidates/decision.json` from the resolved change and delegates the verdict and metrics to `validateCandidates`, building the dependency rules with `buildDependencyRules` and the attributor with the shared `moduleAttributor` over the same module map.
- WHEN the kind runs, THEN it returns the existing `ValidateResult` with `CandidateMetricsFacts` and writes nothing
- WHEN `module-map.yaml` is absent, THEN the rules come from `constitutionFallbackRules()` (reporting `constitution-fallback` as the rule source) and the attributor from the same fallback module map

#### REQ-SERVICES-119: archive summary names the plan decision
`generateSummary` adds a `Plan Decision` line naming the chosen option and its `graded_by` when the change recorded one.
- WHEN quality_log holds a plan sign-off newer than the latest plan verifier result (`hasPlanSignoffAfterVerifier`), THEN the line names that latest sign-off's option with `graded_by: human` — `plan` included — except that a `plan` sign-off of a change whose metadata scale is `full` is not its decision
- WHEN no fresh sign-off counts (none, one a later verifier entry superseded, or a `plan` sign-off at full scale) but a schema-valid `candidates/decision.json` does exist, THEN the line names its `recommended_option` with `graded_by: in-session`; `graded_by` is derived from quality_log, never trusted from decision.json
- WHEN neither exists, or decision.json predates `graded_by` and fails the schema, THEN no line is added and the summary is byte-identical to before

#### REQ-CLI-056: CLI surfaces for the plan sign-off pause
The CLI exposes `--signoff <option>` on `prospec change log`, formats the new routing codes in `prospec status`, and prints the candidate metrics table for `prospec validate candidates`.
- WHEN `--signoff` is combined with `--result`, `--verifier-report`, `--grade`, `--dimension` or review counts, THEN the command refuses before calling the service
- WHEN a route is `AWAITING_HUMAN_PLAN_SIGNOFF`, THEN status prints a HALT line for the pending human sign-off with the `--signoff` command and no station action; an `ESCALATE_TO_HUMAN` route keeps its own HALT and failure summary
- WHEN `validate candidates` succeeds, THEN it prints a table with columns option, direction_violations, touched_modules, estimated_lines and unknown_references in that order
- WHEN help is printed for `status`, `change log` and `validate`, THEN it names `PROSPEC_PAUSE_AT`, a `--signoff` command line in the `change log` Example block and the `candidates` kind

#### REQ-TEMPLATES-236: Autonomous selection without a pause and the opt-in HALT
The rendered plan, ff, candidate-evaluation and cascade-protocol outputs state both selection paths: without a pause the agent selects the winner in-session, records `graded_by: in-session` and continues without asking the human; with the pause the station HALTs for a human sign-off.
- WHEN the no-pause path is described in any of the four outputs, THEN it states the in-session selection and continuation and that the agent NEVER asks the human to choose, and no output requires an unconditional human choice
- WHEN `prospec status` returns `AWAITING_HUMAN_PLAN_SIGNOFF`, THEN plan and ff stop after plan without generating tasks and present, per the `human-decision` reference, the candidate summary, metrics table, in-session rationale and plan verifier report for `scale: full`, and the direction summary for other scales
- WHEN a skill mentions the sign-off command, THEN a NEVER rule forbids running it without an explicit human instruction; plan, ff and cascade-protocol likewise forbid setting `PROSPEC_PAUSE_AT` to skip a pause without one, because the router names that override among its dead-end remedies
- WHEN the human picks an option other than the recommended one, THEN the templates route it through revising plan.md, delta-spec.md and decision.json and re-recording the plan verifier before the sign-off
- WHEN a candidate `call_chain` is authored, THEN each hop starts with a repo-relative path of a code call or import edge; template-file reads are not hops
- WHEN the lifecycle Gates, metadata-format and config-example are rendered, THEN both `_status-lifecycle` copies describe the pause precedence (`PROSPEC_PAUSE_AT`, the AI-proposed Premise, `workflow.pause_at`), the scales it covers, both codes and the sign-off freshness rule including the plan version, metadata-format documents `signoff_option` and both plan-digest stamps, config-example carries the real keys `pause_at: []` with a comment naming `[plan]` and `always_escalate` with its default categories, and the lifecycle `prospec-ff` note states that ff also halts after plan under the pause
