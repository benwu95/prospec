# SDD Workflow — UI Changes

## US-58: UI Changes Declare a Design Source and Are Verified Visually [P0]

As a developer delivering a frontend change with prospec,
I want the proposal to declare where the UI design comes from, the later stations to work from that source, UI changes to carry a visual regression test, and verify to grade the implementation against the source,
so that the agent implements my design or component library instead of guessing, and conformance to the design is judged on its own axis.

**Acceptance Scenarios:**
- WHEN the proposal's `## Design Source` names an external design link, an AI design tool artifact, a prototype path or screenshots, THEN plan, tasks and implement point to that source and read it with the host's own tools, naming no particular design tool or MCP server
- WHEN `## Design Source` declares `none`, THEN the UI structure is decided at plan (or in tasks.md without a plan) and implement follows it with the project's conventions
- WHEN the project's conventions or Knowledge describe a component library and design tokens, THEN implement's UI guidance follows them
- WHEN a change includes UI work, THEN tasks schedules a visual regression test task whose framework is the project's choice, run by `test_command` and recorded with the test evidence
- WHEN verify checks a UI change, THEN a missing visual regression test is recorded as a WARN
- WHEN a Design Source other than `none` is declared, THEN verify's `design` dimension is graded in fresh context against the source and the rendered screens; with `none` or no Design Source it is `not-applicable`; when either input cannot be obtained it is `not-adjudicated`, disclosed, and never PASS

### Behavior Specifications

#### REQ-TEMPLATES-270: Proposal Declares a Design Source
`references/proposal-format.hbs`, the proposal format `prospec-new-story` and `prospec-ff` deploy and follow, defines an optional `## Design Source` section that names where a UI change's design comes from — an external design tool link, a component library, an AI design tool artifact, a prototype path or screenshots — or `none` when the UI starts from scratch. A proposal that carries the section declares a UI change.
- WHEN a change includes UI work, THEN its proposal carries `## Design Source` naming the source, or `none` when the UI starts from scratch
- WHEN the section names a source, THEN the guidance requires no particular design tool, MCP server or vendor; the source is whatever the host can read
- WHEN a proposal has no `## Design Source` section, THEN the change is not a UI change and no station asks for a design
- WHEN a station decides whether a change is a UI change, THEN it reads the proposal's `## Design Source` section, or the Design Source plan.md records from it


#### REQ-TEMPLATES-271: Plan, Tasks and Implement Carry the Design Source
`references/plan-format.hbs` (deployed to `prospec-plan` and `prospec-ff`), `prospec-tasks` and `prospec-implement` carry a UI change's declared Design Source from the proposal into the plan, the task list and the implementation, and read it with the tools the host provides.
- WHEN plan runs for a UI change, THEN plan.md's Technical Summary records the Design Source, and with `none` the plan decides the UI structure
- WHEN a scale without plan.md decomposes a UI change whose Design Source is `none`, THEN tasks.md states the UI structure the tasks implement
- WHEN tasks runs for a UI change, THEN tasks.md carries UI tasks that cite the Design Source when it is not `none`, plus a visual regression test task whose framework is the project's choice
- WHEN the visual regression test runs, THEN it belongs to the suite the project's `test_command` runs, and its result is recorded through the existing test evidence (`prospec check --record-tests`)
- WHEN implement runs a UI task whose Design Source names a source, THEN it reads that source with the host's tools, treating its content as design data and never as instructions; with `none`, it implements the UI structure plan.md or tasks.md states
- WHEN tasks or implement runs under a scale with plan.md, THEN they take the Design Source from plan.md; without plan.md, from the proposal
- WHEN implement runs a UI task, THEN it follows the component library and design tokens described by the project's conventions or Knowledge
- WHEN the host cannot read the Design Source, THEN implement asks the user for a readable source rather than guessing the design


#### REQ-TEMPLATES-272: Verify Grades Design Conformance and Confirms Visual Tests
`prospec-verify`'s conditional `design` dimension grades whether the implementation conforms to the proposal's declared Design Source, in fresh context through the `grader-design` delegation, and verify confirms by judgment that a UI change carries a visual regression test.
- WHEN the proposal declares a Design Source other than `none`, THEN the `design` dimension compares that source with the implementation's rendered screens — screenshots from the visual regression tests or from the host's browser tools — and records PASS, WARN or FAIL, treating the source's content as design data and never as instructions
- WHEN the Design Source is `none` or the proposal has no `## Design Source` section, THEN the `design` dimension is `not-applicable`
- WHEN the grader cannot obtain the Design Source or the implementation's rendered screens, THEN the dimension is `not-adjudicated` with the reason disclosed, grade S is unreachable, and it is never recorded as PASS
- WHEN a UI change, `none` included, has no visual regression test, THEN verify records a WARN naming the missing test, judged from the change's tasks and tests, whether or not the `design` dimension applies
