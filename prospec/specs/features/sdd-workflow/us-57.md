# SDD Workflow — Station Rules at the CLI Boundary

## US-57: Stations Cite Graduated Requirements, Hand the CLI Artifact-Language Text and Read Whole Gate Output [P0]

As a developer whose agent writes trust-zone knowledge, passes free text to the CLI and runs gate commands at review and verify,
I want knowledge-update to cite only requirements the Feature Specs already define, free text bound for change artifacts to follow the artifact language, and review and verify to read each gate command's whole output and judge each state-changing step by its own exit code,
so that dangling references, mixed-language change records and steps recorded after a refused gate are prevented at the station that would cause them.

**Acceptance Scenarios:**
- WHEN knowledge-update writes trust-zone knowledge from a delta-spec, THEN it cites only REQ IDs the Feature Specs already define and describes this change's added or modified requirements by behavior
- WHEN that knowledge is written, THEN the skill runs `prospec check` and confirms `req-references` reports no dangling reference before stamping
- WHEN a skill that includes the Language Policy partial is regenerated, THEN its Language Policy section covers free text handed to the CLI for a change artifact, leaving identifiers, paths, commands and enum values as they are
- WHEN review closes a round or verify records its result with free text for the CLI, THEN that station's instruction asks for the artifact language too
- WHEN review or verify runs a gate command, THEN the skill reads its whole output before the next step and judges each state-changing step by that command's own exit code, not by a command chained after it

---

#### REQ-TEMPLATES-267: Knowledge-update cites only graduated requirements
`prospec-knowledge-update` writes trust-zone knowledge that cites only requirements the Feature Specs already define.
- WHEN Phase 3 writes module README content, THEN the text it writes cites a REQ ID only when a Feature Spec already defines it, and describes the behavior of a requirement this change adds or modifies instead of citing its ID, because that requirement lands in the Feature Specs at archive; the rule requires removing no existing citation
- WHEN that content is written, THEN the skill runs `prospec check` and confirms `req-references` reports no dangling reference before stamping with `prospec knowledge verify`
- WHEN the rule renders, THEN it is one statement in Phase 3's README-authoring section and adds no artifact, CLI gate or stop point

---


#### REQ-TEMPLATES-268: Review and verify read whole gate output and judge each state-changing step by its own exit code
`prospec-review` and `prospec-verify` read each gate command's whole output and judge each state-changing step by that command's own exit code.
- WHEN review's Persistence section or verify's Core Workflow renders, THEN it instructs reading each gate command's whole output before the next step, because circuit-breaker, escalation and refusal messages can appear mid-output, even when the command succeeds
- WHEN a state-changing step runs, THEN the skill runs it as its own command and judges whether it succeeded by that command's own exit code, not by a command chained after it
- WHEN the rule renders, THEN it names no specific shell, filter command, host tool, model or vendor

---


#### REQ-TEMPLATES-269: Review and verify write their quality-log warnings in the artifact language
`prospec-review` and `prospec-verify` write the warning free text they pass to the CLI in the artifact language.
- WHEN review closes a round, THEN an unresolved-item warning is written in the artifact language, while a circuit-breaker warning keeps the CLI's exact `circuit breaker tripped: <type>` form
- WHEN verify records its result with a budget-counted WARN, THEN each `--warning` detail is written in the artifact language

---


#### REQ-TESTS-145: Station rules for references, CLI free text and gate output are pinned section-scoped
`skill-format.test.ts` pins the station rules for graduated references, CLI free text and gate output section-scoped.
- WHEN the bundled templates render, THEN each rule is asserted inside its section: the Language Policy section of every skill that includes the partial, knowledge-update's Phase 3 README-authoring section, review's Persistence and Review Provenance sections, and verify's Core Workflow and Record & Status Update sections
- WHEN any asserted rule is deleted from its section — a partial rule by inlining the partial without that sentence into each includer, after asserting the mutation applied — THEN its assertion turns red
- WHEN the rule text is scanned, THEN it names no forbidden model or vendor, no harness tool or agent type the suite lists, and no issue number
