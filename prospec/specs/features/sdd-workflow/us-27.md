## US-27: Change Metadata as an Enforced Contract [P1]

As a developer using the prospec SDD flow,
I want a structural error in `metadata.yaml` reported at the read that finds it, and every write to be checked before it lands,
So that a broken field never travels silently to a later station that misreads it.

**Acceptance Scenarios:**
- WHEN a station reads metadata whose `status`, `quality_log` entry, or `review_provenance` violates the schema, THEN it throws, naming the change and the offending field path
- WHEN a station writes metadata that violates the schema, THEN the write is refused and the target file is left untouched
- WHEN metadata carries keys the schema does not model, THEN validation passes and those keys survive the round trip unchanged

#### REQ-TYPES-064: Metadata Validation Error and Bare Module Names
Define the metadata contract's error type and the value-level constraints the stations enforce.
- WHEN validation fails, THEN a `MetadataValidationError` (`METADATA_VALIDATION_FAILED`) carries the change name and the zod field paths, and points at the metadata-format reference
- WHEN a `related_modules` entry carries markdown emphasis, backticks, surrounding whitespace, or is empty, THEN it is rejected; a bare name (`types`, `api-middleware`, `user_profile`) is accepted
- WHEN a `dimensions` entry reports a dimension the change's scale, `ui_scope`, or absent Knowledge base skipped, THEN `not-applicable` is valid there — never as the gate-level `result`, which stays the three-state
- WHEN metadata carries unmodeled keys at any level, THEN the schema (loose at every level) keeps them; the sole deliberate divergence is `warnings`, whose default only ever adds the key the format requires
- WHEN a station BUILDS metadata, THEN it uses the strict `NewChangeMetadata` view, because `z.infer` of a loose schema gains an index signature that would disable the excess-property check

#### REQ-LIB-031: Single Validated Entry Point for Change Metadata
`lib/change-metadata.ts` is the only place a station reads or writes a change's `metadata.yaml`.
- WHEN a station reads, THEN it receives both the validated value and the `Document`, so a later write preserves comments and unmodeled keys
- WHEN a station writes, THEN the value is validated first; a rejected write leaves the file byte-identical
- WHEN validation runs, THEN it only inspects — it never rewrites, reorders, or strips the caller's data
- WHEN metadata is written, THEN it goes through `atomicWrite()`; the helper imports only `types` and `lib`

#### REQ-SERVICES-067: Stations Read and Write Metadata Only Through the Helper
The stations that previously cast `doc.toJS() as ChangeMetadata` now go through the shared helper.
- WHEN change-story, change-plan, change-tasks, or `check --record-review` touches metadata, THEN it uses `lib/change-metadata`; no `as ChangeMetadata` cast remains in `services/`
- WHEN those stations meet metadata violating the required-field floor — including a pre-schema record with no `created_at` — THEN they reject it, naming the change and field
- WHEN `archive.service` or `lib/drift-sources` reads metadata, THEN it stays lenient by design: both scan every change directory, so a malformed record must surface as a report or a skip, never as a thrown scan. Archive is the terminal station and must still absorb records the earlier stations now reject; its floor is the archive Entry Gate's `metadata-completeness` check

#### REQ-TESTS-055: Metadata Contract Regression Coverage
Pin the contract against both the failures it must catch and the shapes it must not reject.
- WHEN a corrupted `status`, `quality_log`, or `review_provenance` is read, THEN a test asserts the error names the offending field path
- WHEN metadata carries unmodeled keys or YAML comments, THEN a test asserts a read → modify → write round trip preserves them
- WHEN shapes transcribed from real archived records are validated (grade, `not-applicable` dimension, `archived_at`, review counts), THEN they pass; the two historical malformations (grade in `result`, `warnings` as a string) fail
- WHEN the proposal template renders related modules, THEN a contract test using the real renderer asserts each name is bolded exactly once

## US-28: Deterministic SDD Station Routing [P1]

As an AI agent working a prospec project (resuming work at session start),
I want a `prospec status` command that computes each in-flight change's current node, next station, blocking gates, and reasons from `.prospec/changes/` metadata,
So that station-order derivation is testable deterministic code instead of per-session LLM interpretation of prose.

**Acceptance Scenarios:**
- WHEN a change is at `status: plan` and no premise or other prerequisite blocks advancement, THEN report current node plan and next station `/prospec-tasks`, with the reason citing the lifecycle edge
- WHEN `scale: quick` at `status: story` THEN next is `/prospec-tasks` (the legal skip) — `/prospec-plan` is never suggested
- WHEN `scale: backfill` at `status: implemented` THEN it is judged a legal lifecycle entry (not a skipped station) and routed onward per the review → verify order
- WHEN `status: implemented` THEN review is suggested before verify by workflow order (review owns no status transition; done-ness is read from `review_provenance`)
- WHEN proposal.md declares `ui_scope` full/partial at `status: plan` with no design-spec.md THEN `/prospec-design` is inserted between plan and tasks — never under `scale: quick` (router ruling, recorded in `_status-lifecycle.md`)
- WHEN an active new-contract standard/full premise is incomplete and no pending escalation takes precedence, THEN return to `/prospec-explore` with the gaps; completion restores the applicable lifecycle route without regressing status
- WHEN no non-archived change exists THEN report the clean state
- WHEN a retry bound produces a pending escalation without an applicable grant, THEN status halts with the shared decision; a reasoned current-event grant routes one attempt to its station without forging a PASS or resetting lifetime history.
- WHEN sign-off or Knowledge repair halts routing, THEN its own remedy remains and no retry event is added.

### Behavior Specifications

#### REQ-TYPES-070: Station-Routing Contract and Canonical Order
The types layer defines the SDD station order — including the workflow rank of the no-status-transition design/review/knowledge-update stations and the `promote` backfill entry — and the `ChangeRouteFacts`/`ChangeRoute`/`StatusReport` report contract (current node, next station, blocking gates, reasons, a stable reason `code`, per-change error entries, and the optional drift signal). It also owns `WORKFLOW_REASON_CODES` (frozen) and `WorkflowReason { code, message, remediation }`, shared by the router and the archive gate.
- WHEN the station order is read, THEN `SDD_STATIONS` is `story → plan → design → tasks → promote → implement → review → verify → knowledge-update → archive` (periodic learn excluded from the linear order), and a contract test pins it against the `## Station order` chain carried by both `_status-lifecycle.md` copies — the claim of agreement is enforced, not asserted
- WHEN a station is routed to, THEN `STATION_SKILLS` names the skill that runs it for every station, including `promote` → `/prospec-promote-backfill` and `knowledge-update` → `/prospec-knowledge-update`
- WHEN `promote`'s rank is read, THEN it sits immediately before `implement` — the status a promotion lands at
- WHEN a change cannot be routed, THEN the contract expresses it as a named error entry, never a dropped record
- WHEN the change schema is consulted, THEN `CHANGE_STATUSES`/`CHANGE_SCALES` are unchanged — routing adds no status value
- WHEN `ChangeRouteFacts` is constructed, THEN `knowledgeSyncReasons` carries the `WorkflowReason`s for the change's knowledge-sync gaps, empty when its affected-module Knowledge is current
- WHEN the workspace is clean, THEN `StatusReport` may carry an optional `drift: DriftSignal` — additive and absent whenever there is nothing to say, so every existing consumer of the shape is unaffected
- WHEN a route is computed, THEN `ChangeRoute.code` is a member of `WORKFLOW_REASON_CODES`, and `reasons` stays `string[]` so existing `--json` consumers are unaffected
- WHEN `ChangeRouteFacts` is constructed, THEN `lastPlanVerifierResult` and `lastTasksVerifierResult` carry the latest recorded `prospec-plan` / `prospec-tasks` quality_log result, or null when none
- WHEN `WORKFLOW_REASON_CODES` is read, THEN it includes `ESCALATE_TO_HUMAN` in the routing group (append-only; matched by code)
- WHEN `ChangeRouteFacts` is constructed, THEN it also carries `verifyBelowBarStreak`, `planFlawsStreak`, `tasksFlawsStreak` (non-negative integers) and the resolved `maxStationRetries`
- WHEN a route carries `code: ESCALATE_TO_HUMAN`, THEN `ChangeRoute.next` is `null` while `current` is not `archive`; next uses RouteTarget | null so callers also handle exploration returns
- WHEN a next target can return to exploration, THEN RouteTarget extends SddStation with explore and a corresponding skill mapping; current and the linear SDD_STATIONS order remain unchanged, and CHANGE_STATUSES gains no exploration status.

#### REQ-LIB-035: Pure Route Evaluator
`lib/status-router.ts` exposes the I/O-free `routeChange(facts)` — the executable copy of `_status-lifecycle.md` and the ONLY station-transition authority in `src/`: six-state order, the `scale: quick` story→tasks legal skip, the `scale: backfill` `implemented` entry (absent plan/tasks are its normal state), the design station insertion (`ui_scope` full/partial between plan and tasks, never under a scale with no plan), review done-ness via `review_provenance`, verify B/C/D stay reasons, knowledge-aware routing at `verified` (routing to `archive` when `facts.knowledgeSyncReasons` is empty, to `knowledge-update` when every reason is `KNOWLEDGE_UNSYNCED`, and to a `KNOWLEDGE_INPUT_INVALID` halt otherwise), and the archive gate declarations — Knowledge sync **and** review/test provenance currency. Those gates are **declared, never evaluated**: the router stays I/O-free and never reads the drift report; the gate declarations name the station CLI (`prospec verify record` / `prospec archive` / `prospec change status`) that refuses each gate by reading `prospec check`'s report, so adjudication is the CLI's, never the router's. Every route carries a stable `code` from `WORKFLOW_REASON_CODES`.
- WHEN the full status × scale matrix runs, THEN every computed station matches `_status-lifecycle.md`
- WHEN `scale: quick` at `story`, THEN next is tasks and plan.md is never gated on; WHEN `scale: backfill` at `implemented`, THEN it is a legal entry, not a skip
- WHEN `status: implemented` without `review_provenance`, THEN next is review (by workflow order, not status); with it, next is verify
- WHEN `status: verified` and every reason in `facts.knowledgeSyncReasons` is `KNOWLEDGE_UNSYNCED`, THEN next is `knowledge-update` with code `KNOWLEDGE_UNSYNCED`, a blocking gate citing affected-module knowledge sync, and one reason line per gap reason in the same `formatWorkflowReason` form
- WHEN `status: verified` and `facts.knowledgeSyncReasons` is empty, THEN next is `archive`, and the blocking gates name review/test provenance currency alongside Knowledge sync
- WHEN `status: verified` and any reason in `facts.knowledgeSyncReasons` is not `KNOWLEDGE_UNSYNCED` (a `KNOWLEDGE_INPUT_INVALID` reason, or any other code), THEN next is `null` with code `KNOWLEDGE_INPUT_INVALID` — never `knowledge-update`, which repairs none of those inputs — and the reasons list every gap reason in its `<CODE>: <message> — <remediation>` form (`formatWorkflowReason`, owned by the types layer), `KNOWLEDGE_UNSYNCED` ones included, so each keeps its own code; both `_status-lifecycle.md` copies document this halt
- WHEN the function runs, THEN it performs no I/O (drift-checker evaluator precedent)
- WHEN a scale forbids `plan.md` but not `tasks.md`, THEN `story` routes to `tasks` (the quick skip) — derived from the registry, not from the scale's name
- WHEN a scale forbids both `plan.md` and `tasks.md` and the change has not reached `implemented`, THEN it routes to `promote` with the incomplete promotion as the reason, and its blocking gate names `prospec validate promote-scaffold`
- WHEN such a change reaches `implemented`, THEN routing resumes at the normal review/verify/archive path, and the completed station it reports is `promote` — never `implement`, a station that scale's contract never let it run
- WHEN a scale's contract has no plan, THEN the design station is never suggested for it at any status (design hangs off `plan`), keyed on the artifact registry rather than the scale's name
- WHEN `status: verified` and `facts.lastVerifyGrade` is B, C or D, THEN next is `verify` with code `VERIFY_GRADE_BELOW_BAR` and a reason naming the grade and the remedy (fix the WARN/FAIL items, re-run prospec-verify) — evaluated before the knowledge-sync branch; the persisted status is never regressed
- WHEN `status: plan` and `facts.lastPlanVerifierResult` is `FAIL`, THEN next is `plan` with code `PLAN_VERIFIER_FAILED`, evaluated before the design insertion; WHEN `status: tasks` and `facts.lastTasksVerifierResult` is `FAIL`, THEN next is `tasks` with code `TASKS_VERIFIER_FAILED`
- WHEN a later sink-stamped entry records PASS or WARN, or a nonempty legacy planning bypass with no pending escalation applies, THEN normal routing resumes subject to the opt-in sign-off pause; a structured grant routes back to its event station for one attempt and does not forge a verifier result; unstamped Exit Gate notes remain excluded and BREAK_GLASS_PREFIX remains the shared marker
- WHEN a below-bar verify route reaches maxStationRetries and no applicable unused grant routes to its event station, THEN next is null with ESCALATE_TO_HUMAN and the shared escalation decision before the VERIFY_GRADE_BELOW_BAR fallback
- WHEN a plan or tasks FLAWS streak reaches maxStationRetries and no applicable unused grant routes to its event station, THEN next is null with ESCALATE_TO_HUMAN instead of the verifier-FAIL fallback
- WHEN a station's streak has not reached `facts.maxStationRetries`, THEN the existing route-back and code are unchanged, and **both** `_status-lifecycle.md` copies (canonical `prospec/ai-knowledge/_status-lifecycle.md` and the shipped `src/templates/init/status-lifecycle.md.hbs`) document the same bound
- WHEN the router presents the verify gate, THEN its message delegates current assessment and refusal/remediation to `prospec verify record`, without restating the engine’s applicability predicate
- WHEN a current retry escalation has no applicable unused grant, THEN the route is ESCALATE_TO_HUMAN with its shared decision; lifetime ordinal alone does not block a resolved event
- WHEN sign-off or knowledge-input repair produces HALT, THEN its existing remedy remains and no retry event is created
- WHEN an active new-contract standard/full change has a blocked premise and no pending escalation takes precedence, THEN routeChange returns next explore, code PREMISE_INCOMPLETE and actionable gaps without regressing metadata; completing the premise restores the applicable existing route.

#### REQ-SERVICES-070: Status Service (Scan + Facts + Tolerance)
`status.service.ts` `execute()` scans non-archived changes in `.prospec/changes/`, reads each metadata through the schema-enforced `lib/change-metadata`, collects routing facts (artifact existence, `lib/task-markers` code-task completion, proposal `ui_scope`, provenance/quality_log — including the latest `prospec-verify` grade and the latest `prospec-plan` / `prospec-tasks` gate results — and knowledge sync status), and routes via the pure evaluator. Read-only.
- WHEN metadata is missing or fails the schema, THEN that change yields a named error entry and the rest still route (never a crash, never a silent skip)
- WHEN `.prospec/changes/` is absent or holds no non-archived change, THEN the clean state is reported
- WHEN multiple changes are in flight, THEN each is reported with its own current/next/gates/reasons
- WHEN the service runs, THEN it writes nothing (byte-identical filesystem, test-pinned)
- WHEN a change is at `status: verified`, THEN `collectFacts` sets `knowledgeSyncReasons` to the `knowledgeSyncReasons` of its `findUnsyncedModules` gaps; at every other status the list is empty
- WHEN the clean state is reported and a drift report exists, THEN report its draftable finding count only if it parses through `DriftReportSchema` and its recognized deterministic payload matches a shared live assessment, ignoring generated_at and pure Git trace; otherwise report unusable with unreadable/stale/unprovable, without re-deriving finding attribution
- WHEN the required current snapshot or assessment cannot be proven, THEN the saved report is unprovable rather than current; this diagnostic never writes a report or changes station routing
- WHEN any change is in flight, THEN no drift signal is produced
- WHEN collectFacts reads quality_log, THEN sink-stamped verifier_verdict determines planning results, unstamped Exit Gate notes are skipped, and only a reasoned legacy bypass without a pending event supplies the legacy WARN result; structured grants do not hide a verifier FLAWS
- WHEN collectFacts reads quality_log, THEN shared reducers derive verify B/C/D and planning FLAWS streaks and resolveMaxStationRetries supplies the bound; structured grants do not reset a streak and status remains byte-identical
- WHEN escalation or override history exists, THEN status adds the shared decision and lifetime history including reasons, event bindings, usage and legacy completeness; later PASS does not erase it
- WHEN a legacy retry HALT is currently recognizable, THEN status may project its stable pending anchor without persisting or reconstructing missing past HALTs
- WHEN collecting route facts, THEN status supplies the current shared premise assessment under REQ-LIB-099 and resolves exploration skill identity, path and reference map consistently; legacy limitations are disclosed without writing metadata.

#### REQ-CLI-023: prospec status Command and Formatter
`commands/status.ts` (`registerStatusCommand`) + `formatters/status-output.ts`, registered in `index.ts`; thin delegation to the service, stdout for results, stderr via `handleError`, repo-derived strings through `sanitizeTerminal`.
- WHEN `prospec status` runs, THEN each in-flight change prints name, current node, its `issue` reference (only when the change registered one), next station, blocking gates, and reasons
- WHEN output renders, THEN free-form strings pass `sanitizeTerminal`; errors route to stderr
- WHEN the real CLI is exercised end-to-end, THEN the clean-state and in-flight scenarios pass
- WHEN the clean state carries a drift signal, THEN the block names either the draftable finding count and the drafting command, or why the report cannot be used and the command that regenerates it
- WHEN a change's reasons render, THEN each `reason:` line is prefixed with the route's stable `[CODE]`
- WHEN the service provides a next-station reference map, THEN the human-readable formatter prints its ordered phase-to-path entries and purposes after action, retaining all existing status, issue, next, gate, reason and warning output.
- WHEN a map contains repository-derived paths or condition text, THEN terminal output sanitizes those values and the formatter performs no routing or applicability decisions.
- WHEN a route carries `code: ESCALATE_TO_HUMAN` with `next: null` on a non-archived change, THEN the formatter prints a HALT directive and the recorded WARN/FAIL summary, distinct from the terminal `archived` guidance, and prints no `nextSkill` or fallback path

#### REQ-TESTS-058: Routing Test Matrix and Contract Updates
Unit (router full status × scale matrix, service memfs tolerance, formatter), contract (entry-config positive/negative Session Start assertions, dual-copy lifecycle markers), e2e (`prospec status`); the archive back-run is one-off verify evidence, with committed fixtures carrying the per-station pins.
- WHEN the router matrix runs, THEN six statuses, the quick skip, the backfill entry, B/C/D stays, and design/review placement are all covered
- WHEN service tests run, THEN invalid metadata, missing metadata, unparseable YAML, empty dir, and multi-change scenarios are covered
- WHEN contract assertions run, THEN they are section-scoped and mutation-verified (bundled templates are the render source — mutations must target the bundle)

#### REQ-SERVICES-095: status reports the drift report's state, not a re-derived attribution
`prospec status` reports whether the drift report can be trusted and what it says, without re-deriving finding attribution.
- WHEN no change is in progress and a recognized report parses through `DriftReportSchema` and its deterministic payload matches the shared live assessment after ignoring generated_at and pure trace, THEN status reports its DRAFTABLE count through the existing `isDraftableFinding` predicate and recommends drafting; a current zero count produces no signal
- WHEN the report is malformed or off-schema, THEN report unusable/unreadable; WHEN a recognized deterministic payload differs from a provable current assessment, THEN report unusable/stale and recommend regenerating the report, never a silent pass
- WHEN the report has no recognized snapshot version/scope or no measured identity, THEN report unusable/unprovable instead of declaring a legacy digest current or claiming it was measured-and-wrong
- WHEN the current snapshot or assessment cannot be computed, THEN report unusable/unprovable with its reason rather than infer current state from a saved report; neither report reading nor live comparison writes files or reruns tests
- WHEN any change is in progress, THEN no drift signal is produced
- WHEN a change is named with a `fix-` prefix, THEN it receives no special routing, badge, or flag — the prefix is a naming convention, not a provenance mark

#### REQ-SERVICES-111: Resolved and Filtered Status Reference Maps
The status service attaches an additive next-station reference map derived from STATION_REFERENCES to each routed change. It filters known scale and UI-scope predicates using collected facts and resolves paths with the same configured-agent deployment metadata used by agent sync and nextSkillPath; routing remains read-only and unchanged.
- WHEN quick, standard, full or backfill routes are produced, THEN the map includes only applicable phase entries in registry order, with phase, reference path, one-line purpose and any undecidable runtime condition.
- WHEN UI scope is full, partial, none or absent, THEN filtering preserves the router's existing semantics, and unknown conditions are shown as conditional guidance rather than silently discarded.
- WHEN multiple hosts share an output directory, THEN reference paths agree with the resolved nextSkillPath directory and contain no hardcoded host root.
- WHEN no agent is configured or the route is terminal, THEN no deployment path is fabricated; reference-free stations have an empty map.
- WHEN requesting structured status output, THEN the existing fields retain their meaning and the reference map is additive.

#### REQ-TYPES-101: Station-retry bound configuration
The config schema carries an optional `workflow.max_station_retries` (positive integer) bounding the station-to-station recovery loops, and the types layer exports `DEFAULT_MAX_STATION_RETRIES` (3) as the single shipped default.
- WHEN `.prospec.yaml` omits `workflow` or `workflow.max_station_retries`, THEN the config still parses and the bound resolves to `DEFAULT_MAX_STATION_RETRIES` (3)
- WHEN `workflow.max_station_retries` is a positive integer, THEN that value is the resolved bound
- WHEN the field is 0, negative, or non-integer, THEN the resolver falls back to `DEFAULT_MAX_STATION_RETRIES` rather than disabling the bound

#### REQ-LIB-082: Pure station-retry bound resolver
`lib/config.ts` exposes `resolveMaxStationRetries(config)` — a pure resolver returning the configured `workflow.max_station_retries` or `DEFAULT_MAX_STATION_RETRIES`.
- WHEN config is null or omits the field, THEN it returns `DEFAULT_MAX_STATION_RETRIES`
- WHEN the field is a positive integer, THEN it returns that value
- WHEN the field is ≤ 0 or non-integer, THEN it returns `DEFAULT_MAX_STATION_RETRIES`, and no I/O is performed
