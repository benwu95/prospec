# SDD Workflow — Bounded Human Decisions

## US-50: Human Decisions Are Presented Comparably and Delegated Within Bounds [P1]

As a maintainer answering a workflow decision point,
I want every option presented with its reversal cost, the recommendation's evidence and the strongest alternative's condition, and a general "follow your recommendation" never to decide re-scoping, Break-Glass overrides or breaking changes,
so that a wrong direction surfaces before implementation while a specific decision I already made is not asked again.

**Acceptance Scenarios:**
- WHEN `.prospec.yaml` omits `workflow.always_escalate`, THEN the config still loads with the default categories `re-scope`, `break-glass-override` and `breaking-change`, and an invalid value is refused
- WHEN a pending decision falls in one of those categories and the human has only delegated generally, THEN the skill asks for it; when the human already named that specific change, THEN it proceeds
- WHEN a standard plan pauses for sign-off, THEN the human sees at most six direction points and three response paths, with no candidate files required

**Independent Test:**
Config unit tests cover absent, default, deduplicated and invalid categories; `skill-format` pins the single `_human-decision` definition, the six points, the three responses and the delegation boundary.

#### REQ-TYPES-113: Escalation category configuration contract
The config schema carries an optional `workflow.always_escalate` declared as unknown-shaped data; the types layer exports `ALWAYS_ESCALATE_CATEGORIES` (`re-scope`, `break-glass-override`, `breaking-change`) and `DEFAULT_ALWAYS_ESCALATE` (all three), each a workflow decision with a project-agnostic meaning — `breaking-change` takes back or narrows behavior a graduated requirement promises (a delta-spec REMOVED entry or `**Dropped:**` bullet) — and `AlwaysEscalateInvalid` (`ALWAYS_ESCALATE_INVALID`) is the error a malformed value raises.
- WHEN `.prospec.yaml` omits `workflow.always_escalate`, THEN the config parses exactly as before
- WHEN `workflow.always_escalate` has any shape, THEN config parsing itself still succeeds and validation is left to the resolver
- WHEN `AlwaysEscalateInvalid` is raised, THEN its message names `.prospec.yaml workflow.always_escalate` and the offending value, and its suggestion lists the valid categories

---


#### REQ-LIB-102: Escalation category resolver
`lib/config.ts` exposes `resolveAlwaysEscalate(config)`, a pure resolver returning the categories that a general delegation ("follow your recommendation") never decides.
- WHEN the config is absent or omits `workflow.always_escalate`, THEN it returns `DEFAULT_ALWAYS_ESCALATE`
- WHEN the value is an array of known category names, THEN it returns them with duplicates removed in first-seen order; an empty array is a valid value
- WHEN the value is not an array, holds a non-string, or names a category outside `ALWAYS_ESCALATE_CATEGORIES`, THEN it throws `AlwaysEscalateInvalid` rather than ignoring the value

#### REQ-TEMPLATES-247: Shared human-decision presentation contract and reference
The `_human-decision` partial is the single definition of how a human decision is presented, rendered into the `human-decision` reference (deployed to plan, ff and new-story) and the `cascade-protocol` Tastemaker presentation.
- WHEN a decision is presented, THEN each viable option states its concrete reversal cost, the recommendation cites its rule or evidence, and the strongest non-recommended option states the condition under which it would be right
- WHEN a decision was already supplied, or Draft-First selects the scale autonomously, THEN the contract adds no question
- WHEN a standard change reports `AWAITING_HUMAN_PLAN_SIGNOFF`, THEN plan and ff present at most six points drawn from the existing plan (purpose, direction with its evidence, scope, key assumptions, the strongest alternative with its condition, reversal cost now versus after implementation) with references to the full plan and verifier report, and require no candidates or metrics
- WHEN the human approves, adjusts named details, or rejects the direction, THEN the reference routes to recording the sign-off, to updating the plan and re-verifying the affected parts, or to `prospec-explore` through the existing Story and amendment flow, respectively
- WHEN plan, ff or new-story reach a human decision point, THEN they load the `human-decision` reference there, and the rendered set names no harness-specific question tool or option-marker convention

#### REQ-TEMPLATES-248: Bounded general delegation and specific authorization
The `human-decision` reference states the delegation boundary: a general delegation never decides a category in `workflow.always_escalate`, while a decision the human already stated specifically is reused rather than asked again.
- WHEN a pending decision falls in a configured `always_escalate` category and the human has only given a general delegation, THEN the agent asks for that decision; when the human already named that specific change, THEN the agent proceeds on it
- WHEN the human answers "change X, then continue", THEN that answer authorizes the named change and the continuation once the plan is updated and the affected verification is re-recorded, and a newly arising scope, breaking-change or major trade-off decision is asked anew; an answer too vague to define the change is clarified first
- WHEN a Break-Glass override or an acceptance amendment is involved, THEN the reference adds no gate and defers to the station's escalation guidance and the amendment command, naming the CLI as checking those structured records and the skill as judging whether a conversation is a specific authorization
- WHEN `PROSPEC_PAUSE_AT` releases the plan pause, THEN no other gate or delegation boundary is released; who may set it follows REQ-TEMPLATES-236
