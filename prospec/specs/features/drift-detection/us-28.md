## US-28: Full test runs take turns in one repository test queue [P0]

As a developer running several agents in different worktrees of one repository,
I want full test runs to start one at a time, in ticket order, whether they come from `prospec check --record-tests` or from `prospec exclusive`,
so that one agent's run is not affected by another's, and an interrupted run leaves nothing running beside the next one.

**Acceptance Scenarios:**
- WHEN two worktrees run `prospec check --record-tests` at the same time, THEN the later ticket starts after the earlier run ended, and three or more callers start in ticket order with no unexpired earlier ticket overtaken
- WHEN no other run is in progress or waiting, THEN the command runs at once and the test attempt and test provenance rules are unchanged by the queue
- WHEN the command holding the turn on this host has ended without releasing it and every test process it started has ended, THEN the next ticket takes the turn without manual cleanup
- WHEN the running suite itself calls a queued entry, THEN that call does not wait for the turn it runs under
- WHEN the wait cap passes, THEN the command ends with the busy exit code and prints its own ticket, the tickets ahead and the holder's worktree, start time and change or command, leaving the change's test attempt and test provenance as they were
- WHEN the same command is re-run within the lease, THEN it keeps its ticket and place; a ticket not re-run within the lease expires and a later run joins at the tail
- WHEN a run exceeds its time limit, THEN every process it started is killed and the attempt is recorded as a timeout; WHEN prospec receives an interrupt or termination signal, THEN the run's processes are killed before the turn is released
- WHEN prospec is killed with no chance to react while the test processes still run, THEN the next ticket does not start and the busy output says the turn is held by what was left running; past that run's time limit the next ticket kills those processes and starts
- WHEN the platform has no process groups, THEN the limits of the kill are stated in both CLI reference languages and the output claims nothing beyond them
- WHEN `prospec exclusive -- <command>` wraps a command, THEN it shares the queue and order with `--record-tests`, runs the command once it holds the turn and exits with that command's exit code, and reports busy without running it when the wait cap passes
- WHEN an agent follows a skill to a step that needs a full suite, THEN the guidance sends it through `--record-tests` or `prospec exclusive`, tells it to re-run the same command on busy and never to run the test command directly, and names no host-specific tool, timeout value or background mechanism
- WHEN the CLI reference is read in English or Traditional Chinese, THEN both describe `prospec exclusive`, the busy result and the queue settings

#### REQ-TYPES-119: Test queue contracts and configuration keys
`types/test-queue.ts` owns the test queue's persisted and cross-layer contracts: `TestQueueStateSchema` (a version, the next sequence number and the tickets), `ProcessIdentity` (a pid and the start reading taken for it, or null), `TestQueueBusy`, `TEST_QUEUE_BUSY_EXIT_CODE` (75), `TEST_QUEUE_TOKEN_ENV` (`PROSPEC_TEST_QUEUE_TOKEN`) and the default limits `TEST_QUEUE_PREPARE_LIMIT_MS` (600000), `TEST_QUEUE_DEADLINE_GRACE_MS` (60000), `TEST_QUEUE_MUTEX_WAIT_MS` (10000) and `TEST_QUEUE_POLL_MS` (1000). `tech_stack.test_queue_wait_ms` and `tech_stack.test_queue_lease_ms` are declared the way `tech_stack.test_timeout_ms` is and resolved in `lib/config.ts`.
- WHEN a ticket is waiting, THEN it carries its sequence number, key, label, worktree, host, its own lease and its last heartbeat
- WHEN a ticket holds the turn, THEN it also carries a token, the holder's `ProcessIdentity`, the grant time, a phase (`preparing`, `spawning` or `running`), a deadline and the trees registered under it, each a kind and a `ProcessIdentity`
- WHEN persisted state has an unknown version or a shape the schema does not declare, THEN `TestQueueStateSchema` rejects it
- WHEN `test_queue_wait_ms` is absent, THEN the wait cap resolves to 60000; WHEN `test_queue_lease_ms` is absent, THEN the lease resolves to 300000
- WHEN `test_queue_wait_ms` is not an integer from 0 to 2147483647, or `test_queue_lease_ms` is not an integer from 30000 to 2147483647, THEN its resolver throws a typed error naming the key

#### REQ-LIB-112: Test queue decision engine
`lib/test-queue-engine.ts` holds the queue rules as pure functions over a state, a request and injected facts: the current time, this host's name, and for each holder and tree one of the three statuses REQ-LIB-114 defines — `gone`, `alive` or `unknown`. It reads no file, process or clock. A ticket holding the turn leaves the queue through a release or through one of the two removal bullets below, and is kept in every other combination of statuses.
- WHEN an acquire request's key has no waiting ticket, THEN a ticket with the next sequence number is appended; WHEN the key has a waiting ticket, THEN that ticket is kept and its heartbeat refreshed
- WHEN no ticket holds the turn and the request's ticket has the lowest sequence number, THEN it is granted the turn in phase `preparing` with a new token, the grant time and a deadline of the grant time plus `TEST_QUEUE_PREPARE_LIMIT_MS`; otherwise the decision is waiting, with the number of tickets ahead and the ticket holding the turn when one does
- WHEN the request's key is that of the ticket holding the turn and the request does not carry its token, THEN it is numbered as any other request: it takes, or keeps, a waiting ticket of its own behind that ticket
- WHEN a waiting ticket's heartbeat is older than that ticket's lease, THEN it is removed before the request is matched, so a request whose ticket expired receives a new sequence number
- WHEN a ticket holding the turn was written by this host and its holder is `alive`, THEN it is kept
- WHEN a ticket holding the turn was written by this host, its holder is `gone` and every registered tree is `gone`, THEN it is removed — unless it is in phase `spawning`, where it is kept until its deadline
- WHEN a ticket holding the turn was written by this host, the current time is past its deadline and its holder is not `alive`, THEN the decision's `overdue` lists its registered trees that are `alive`, and the ticket is removed once none is
- WHEN a ticket was written by another host, THEN no status is consulted for it: holding the turn it is kept, and waiting it is removed by its lease alone
- WHEN the granted caller asks to enter `spawning`, THEN phase `preparing` becomes `spawning` with the requested deadline; WHEN the granted caller registers the tree it spawned, THEN the phase becomes `running`; a re-entrant registration leaves the phase and the deadline unchanged
- WHEN an acquire request carries the token of the ticket holding the turn on this host, THEN the decision is `reentrant`, no ticket is added, and that caller sends only re-entrant requests to register and unregister a tree
- WHEN a request to enter `spawning`, register, unregister or release carries a token that no ticket holding the turn carries, THEN the decision is `lost`
- WHEN the granted caller's release is decided, THEN the decision lists the trees still registered under the ticket and removes the ticket

#### REQ-LIB-113: Test queue store and turn lifecycle
`lib/test-queue.ts` keeps one queue per git repository in `<git-common-dir>/prospec/test-queue/` and applies each state change as read, engine decision (REQ-LIB-112) and write inside a mutex. `withTestQueue(request, body)` is the acquire → run → release path of both entries.
- WHEN the queue directory is resolved, THEN it comes from `git rev-parse --path-format=absolute --git-common-dir` through `gitRead`, as a real path
- WHEN the mutex is taken, THEN its owner file is created through `fs-utils`' no-clobber create — the helper `createTicketExclusive` also delegates to — and it is removed by the owner whose token it holds
- WHEN an existing mutex names a pid of this host that is `gone`, THEN the remover creates a guard directory with `mkdir`, reads the mutex again and removes it only if it still carries the same owner token; an existing guard is left in place
- WHEN the mutex cannot be taken within `TEST_QUEUE_MUTEX_WAIT_MS`, THEN a typed error names the mutex path, the guard path and the recorded owner, and `body` is not called
- WHEN the state file is absent, THEN the queue is empty; WHEN it cannot be read, is rejected by `TestQueueStateSchema`, or the directory cannot be written, THEN a typed error naming the path is thrown and `body` is not called
- WHEN a caller passes limits in its request, THEN they replace the defaults of REQ-TYPES-119 for that call; the two entries pass none
- WHEN the engine lists an overdue tree, THEN the transaction asks REQ-LIB-114 to kill it and writes the state unchanged; the ticket is evaluated again at the caller's next poll
- WHEN the turn is not granted, THEN `withTestQueue` polls every `TEST_QUEUE_POLL_MS` and refreshes its ticket's heartbeat until the wait cap, and at the cap returns a `TestQueueBusy` — the ticket number, the tickets ahead, the queue path and, when a ticket holds the turn, its label, worktree, host, grant time, whether it was written by another host and whether its holder is `gone` — without calling `body`; a wait cap of 0 makes one attempt
- WHEN the turn is granted, THEN `body` receives a session whose `run` enters `spawning` with a deadline of the current time plus the run's timeout plus `TEST_QUEUE_DEADLINE_GRACE_MS`, runs the command with the token in the child's `PROSPEC_TEST_QUEUE_TOKEN`, and registers the spawned tree
- WHEN entering `spawning` is decided `lost`, THEN `run` spawns nothing and reports the run as not started; WHEN registering the spawned tree fails or is decided `lost`, THEN `run` kills that tree and reports the run as lost
- WHEN the granted caller's `body` returns or throws, THEN the turn is released in one transaction: the trees the release decision lists that are `alive` are killed before the state without the ticket is written; a release that fails is reported as a warning beside the value `body` returned, and when `body` threw its error is rethrown as it is
- WHEN the decision is `reentrant`, THEN `body` runs without waiting, its `run` registers its tree under the holder's ticket and unregisters it when the command ends, and no release is sent

#### REQ-LIB-114: Process-tree runner
`lib/process-tree.ts`'s `runProcessTree(argv, options)` runs one command without a shell and with inherited stdio, and owns its timeout, its interruption and the reach of its kills. A `ProcessProbe` — the host's unless `options` carries another — supplies the platform, the existence check, the `ps` reading, the signal and `taskkill`; the spawn options, the start reading, the statuses and the kill are decided from it.
- WHEN the platform is not `win32`, THEN the command is spawned as the leader of a new process group, a kill sends SIGKILL to the group, and a pid is read with `ps -o stat= -o lstart= -p <pid>` under `LC_ALL=C` and `TZ=UTC`: the start reading is the `lstart` text, or null when the command fails
- WHEN the platform is `win32`, THEN the command is spawned as an ordinary child, its start reading is null, and a kill runs `taskkill /pid <pid> /T /F` and then kills the process
- WHEN a holder's status is asked, THEN it is `gone` when signal 0 to its pid reports no such process or its `ps` state begins with `Z`; otherwise `alive` when a fresh start reading equals the recorded non-null reading; otherwise `unknown` — a failed `ps` never yields `gone`; start readings are compared as strings and never parsed
- WHEN a tree's status is asked where the tree is a process group, THEN it is `gone` only when signal 0 reports neither the leader pid nor any member of the group, `alive` when the leader's `ps` state does not begin with `Z` and its fresh start reading equals the recorded non-null reading, and `unknown` otherwise — including a group whose leader ended or is unreaped while a member remains; on `win32` a tree's status is its process's, by the holder rule
- WHEN a process other than the one that spawned a tree is asked to kill it, THEN it reads the tree's status again and kills only if it is `alive`
- WHEN the runner's own timer expires, THEN it kills the tree it spawned and reports `timed_out` with no exit code, whichever exit code or signal the command reports
- WHEN the runner receives SIGINT, SIGTERM or SIGHUP while the command runs, THEN it kills the tree it spawned and reports that signal as the interruption; its handlers are removed when the run settles
- WHEN the command ends on its own, THEN its exit code or terminating signal is reported as observed and the runner kills nothing
- WHEN the command cannot be spawned, THEN the spawn error is reported and no tree is handed to the caller
- WHEN a tree is spawned, THEN the caller's `onSpawn` receives it, with its start reading, before the runner waits for the exit
- WHEN a descendant starts its own session or process group, THEN no kill and no status reaches it; WHEN the leader has ended, THEN the group's remaining members are `unknown` and no other process kills them; on `win32` a descendant that outlives the spawned process is reached by neither the status nor the kill

#### REQ-SERVICES-132: Exclusive command service
`exclusive.service.execute` runs one argv under the repository's test queue turn and reports how it ended. It writes no change metadata.
- WHEN it acquires, THEN the ticket key is built from the project root's real path and the argv, the label is `exclusive` followed by the argv, and the wait cap and lease come from their resolvers
- WHEN the turn is granted, THEN the argv runs through `runArgv` with the cap `resolveTestTimeoutMs` returns, and the result carries the command's exit code, or its terminating signal, timeout, interruption, spawn error or lost turn
- WHEN `withTestQueue` returns busy, THEN the result carries the `TestQueueBusy` and the argv is not run
- WHEN the argv is empty, THEN a typed error states the usage

#### REQ-CLI-065: `prospec exclusive` and queue outcome rendering
`prospec exclusive -- <command> [args…]` is a top-level command over `exclusive.service`, listed in `HELP_ENRICHED_COMMANDS`. `check --record-tests` and `exclusive` render queue outcomes through one formatter, and repo-sourced strings in that output pass `sanitizeTerminal()`.
- WHEN the wrapped command exits, THEN the CLI exits with the command's exit code; WHEN it ended by timeout, terminating signal, spawn error or a lost turn, THEN the CLI exits 1 and a line on stderr names the cause
- WHEN either entry returns busy, THEN the exit code is 75 and the output states the ticket number, the tickets ahead, the holder's label, worktree, host and grant time when a ticket holds the turn, that nothing was run, that re-running the same command within the lease keeps the place, and that the wrapped or test command is not to be run directly instead
- WHEN the busy holder was written by another host, or its holder is `gone`, THEN the output states that fact and the queue path
- WHEN an entry begins to wait, THEN one line on stderr names the ticket holding the turn
- WHEN a run was interrupted by a signal, THEN the exit code is 128 plus the signal's number
- WHEN `exclusive` prints its own messages, THEN they go to stderr
- WHEN the CLI reference and the configuration reference describe these entries, THEN the English and Traditional Chinese files each cover the command, the busy outcome and its exit code, the two configuration keys, the queue's location and its manual removal, that the time an abandoned turn stays held grows with `test_timeout_ms`, and the limits of REQ-LIB-114 — its last bullet, the absence of a start reading on `win32` and wherever `ps` cannot be run, that a tree whose status is `unknown` past its deadline is left running when its ticket is removed, and that a host which kills only the CLI's process group leaves the command running under its ticket
