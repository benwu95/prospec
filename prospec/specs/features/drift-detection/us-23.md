## US-23: knowledge-size ratchet fails growth of over-budget L1/L2 files [P0]

As a maintainer who gates CI with `prospec check --strict`,
I want a change that grows an already over-budget (or newly over-budget) L1/L2 knowledge file to fail `knowledge-size`,
so that knowledge files cannot keep growing silently, while existing overage need not be paid off in a single change.

**Acceptance Scenarios:**
- WHEN the ratchet is enabled and an L1 or L2 file that was over budget at the merge-base is now larger in tokens (or, for L2, lines), THEN `knowledge-size` reports FAIL naming the merge-base value, the current value and the budget, and `--strict` exits 1
- WHEN that file's size is unchanged or smaller, THEN it still reports WARN, as before
- WHEN an L1/L2 file was absent or within budget at the merge-base and is over budget now, THEN it reports FAIL
- WHEN `.prospec.yaml` has no ratchet setting, THEN the `knowledge-size` findings are identical to those before the ratchet existed, all WARN
- WHEN the ratchet is enabled and a Demand, Feature Spec, skill or reference file grows, THEN it still reports WARN only
- WHEN the configured base ref does not exist or has no common ancestor with HEAD (for example a shallow clone), THEN `knowledge-size` reports FAIL explaining the reason and the fix
- WHEN the project is not a git repository and the ratchet is configured, THEN it also reports FAIL, never WARN, PASS or skipped

#### REQ-TYPES-117: knowledge.size_ratchet config and the ratchet finding fields
`KnowledgeSchema` declares an optional `size_ratchet` key whose value the schema accepts in any shape: REQ-LIB-107 reads its `base` — the git ref the ratchet compares against — and grades any other shape, an empty base, or a base git would read as an option as unresolvable, so a mistyped ratchet fails the knowledge-size check instead of making every command that reads the config fail. It lives beside `token_budget`, not inside it, so `TokenBudgetSchema`'s key set and REQ-TYPES-061's key-set contract are unchanged. `KnowledgeSizeFindingSchema` gains three optional fields, present only on an over-tier finding of a ratchet-governed item while the ratchet is resolved: `base_commit` (the merge-base commit) on every such finding, plus either `base_actual` — the same unit's value at the merge-base, or `null` when the file did not exist there — or `ratchet_skipped`, the reason the ratchet was not applied to that file. A report without them still validates.
- WHEN `.prospec.yaml` omits `knowledge.size_ratchet`, THEN the config validates and the ratchet is off
- WHEN `knowledge.size_ratchet` is not a mapping, or its `base` is missing, empty, not a string or starts with `-`, THEN the config still validates and REQ-LIB-107 reports the ratchet unresolvable
- WHEN a report's knowledge-size finding carries none of `base_commit`, `base_actual` or `ratchet_skipped`, THEN it still parses through `DriftReportSchema`

#### REQ-LIB-107: knowledge-size ratchet against the merge-base
When the knowledge base exists and `knowledge.size_ratchet` is present, `collectKnowledgeSize` validates its shape and resolves `git merge-base <base> HEAD` in the project directory and measures at that commit every item that is over a budget now and whose kind's `KNOWLEDGE_SIZE_RULES` entry declares `ratchet: true` (`l1` and `l2`), reading the blob through `git cat-file --filters` so the base text has the same end-of-line and filter conversion as the working-tree file, and using the same `estimateTokens` / `countLines` as the current measurement; a path absent from the merge-base tree is recorded as absent, never as size zero, and a path that is a symlink at the merge-base, or that is or passes through a symlink in the working tree, is not ratcheted — its blob is the link target, not the content measured — and its finding carries `ratchet_skipped` naming that reason. `evaluateKnowledgeSize` then grades each budget unit (tokens, and lines where the rule has a `lineKey`) of a ratchet-governed item independently: a unit over its budget whose merge-base value is absent or smaller than the current value is a `fail` finding whose detail names the merge-base commit, the merge-base value, the current value, the budget and the kind's remedy, and whose `knowledge_size` carries `base_commit` and `base_actual`; every other over-budget unit keeps its existing warn finding, with `base_commit` and `base_actual` (or `ratchet_skipped`) added. A configured ratchet that cannot be resolved — a `size_ratchet` value that is not a mapping, a `base` that is missing, empty, not a string or starting with `-`, not a git work tree, a shallow clone or a failed shallow probe, an unknown ref, no common ancestor, a failed tree or blob read, or any of these git reads exceeding 30 seconds — makes the source's ratchet unresolvable, keeps every item and its existing warn grading, and adds one `fail` finding on `.prospec.yaml` naming the base, the reason and the fix, which carries no `knowledge_size` object because it measures no file; it is never reported as warn, pass or skipped, because `--strict` does not fail on a skipped check; an absent knowledge base still skips the whole check first, ratchet or not.
- WHEN the ratchet is configured and an over-budget L1 or L2 file's tokens exceed its merge-base tokens, THEN the knowledge-size check reports a fail finding with `base_actual` and `--strict` exits 1
- WHEN the same file's size is equal to or smaller than at the merge-base, THEN it keeps the warn finding it has today
- WHEN an L1 or L2 file is absent at the merge-base, or was within budget there, and is over budget now, THEN it reports fail
- WHEN only an L2 file's line count grew past both its merge-base count and the line budget, THEN the line finding is fail and the token finding is graded on its own
- WHEN a `spec`, `demand-knowledge`, `skill` or `reference` file grows while over budget, THEN it reports warn only
- WHEN the configured ratchet cannot be resolved, THEN one fail finding on `.prospec.yaml` names the reason and the item findings stay warn without ratchet fields
- WHEN the ratchet is not configured, THEN the knowledge-size findings are identical to those produced without this requirement
- WHEN the working tree uses CRLF through `core.autocrlf` and the committed blob uses LF, THEN an unchanged file is not reported as grown
- WHEN a ratchet-governed file is a symlink, THEN it keeps the warn grading and its finding carries `ratchet_skipped` instead of `base_actual`

#### REQ-TEMPLATES-255: the ratchet is documented where users configure and read it
`src/templates/references/config-example.yaml.hbs` declares `knowledge.size_ratchet.base` with a comment stating that the ratchet is off when the key is absent, that it fails an over-budget L1/L2 file that grew past its merge-base size, that CI needs full git history, and that a renamed, untracked or ignored L1/L2 file is new at the merge-base and therefore fails whenever it is over budget. `src/templates/skills/references/drift-report-format.hbs` documents the `knowledge_size` fields `base_commit`, `base_actual` and `ratchet_skipped`, the conditions under which `knowledge-size` reports fail, and that the unresolvable-ratchet finding carries no `knowledge_size`.
- WHEN a user runs `prospec config example`, THEN the output shows `knowledge.size_ratchet.base` and parses through `ProspecConfigSchema`
- WHEN an agent reads the drift report format reference, THEN it learns which knowledge-size findings can be fail and what `base_commit`, `base_actual` and `ratchet_skipped` mean

#### REQ-TESTS-142: knowledge-size ratchet tests
Pure unit tests cover every REQ-LIB-107 grading scenario and are mutation-verified (turning the fail back into warn turns them red); an integration test over a real git repository covers merge-base measurement, a project in a repository subdirectory, a CRLF working tree, a symlinked knowledge file, and each unresolvable cause (no git, shallow clone, unknown ref, a base with no common ancestor). Every git-bound test file declares a file-level `testTimeout`.
- WHEN the ratchet's growth comparison is reverted to always-warn, THEN the unit suite fails
- WHEN the collector reads a base path relative to the repository root instead of the project directory, THEN the subdirectory integration case fails
